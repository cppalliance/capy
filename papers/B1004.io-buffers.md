# I/O Buffers for Modern C++

## Abstract

Network and file I/O in C++ demands a vocabulary for describing memory regions. The reflexive modern answer—`std::span<std::span<std::byte>>`—forces allocation for composition and makes semantic claims about buffer contents that raw I/O should avoid. This paper proposes `const_buffer` and `mutable_buffer` types along with `ConstBufferSequence` and `MutableBufferSequence` concepts, drawing heavily from Christopher Kohlhoff's Networking TS and Boost.Asio—a proven design with over 20 years of implementation experience—to enable zero-allocation composition, scatter/gather I/O, and user extensibility through `tag_invoke` customization points.

---

## 1. Motivation

Ask a group of C++ programmers how to represent a buffer for network I/O, and you'll hear a consistent answer: `std::span<std::byte>`. Modern. Type-safe. What more could you need?

Follow up with scatter/gather I/O—sending multiple discontiguous memory regions in a single operation—and the answer extends naturally: `std::span<std::span<std::byte>>`. This mirrors the venerable POSIX pattern:

```cpp
struct iovec {
    void*  iov_base;  // pointer to buffer
    size_t iov_len;
};

ssize_t writev(int fd, const struct iovec* iov, int iovcnt);
```

Scatter/gather via `iovec` arrays enables efficient vectored I/O. The `span<span<byte>>` answer seems like a reasonable C++ equivalent—but it has a fundamental limitation: **arrays of buffers don't compose without allocation**.

Consider combining `HeaderBuffers` (2 spans) with `BodyBuffers` (3 spans):

```cpp
std::vector<std::span<const std::byte>> combined;
combined.insert(combined.end(), header.begin(), header.end());
combined.insert(combined.end(), body.begin(), body.end());
send(combined);  // allocation required
```

Every composition allocates. The concrete type choice—however intuitive—prevents zero-allocation buffer composition.

Even `std::byte` itself is the wrong choice. Notice that POSIX uses `void*`, not `char*` or `unsigned char*`. The `void*` makes no semantic claim about the buffer's contents—it says "this is raw memory; I will move bytes without opining on what they represent." But `std::byte` *is* an opinion: it says "these are bytes, and you can perform bitwise operations on them." The deeper problem is that `span<void>` doesn't compile—`void` is incomplete. This forces a false choice between imposing semantic opinions or abandoning span entirely. Traditional I/O interfaces got this right by staying semantically neutral.

We need abstractions that:

1. Describe contiguous memory without semantic claims
2. Enable scatter/gather through composable sequences
3. Support user-defined buffer types through concepts
4. Map efficiently to OS primitives

---

## 2. Design Goals

### Zero-Allocation Composition

Buffer sequences should compose at compile time:

```cpp
auto combined = buffer_cat(header_buffers, body_buffers);
send(combined);  // no allocation, single writev() call
```

This is impossible when the buffer representation is a concrete array type like `span<span<byte>>`.

### Scatter/Gather I/O

A single operation should accept multiple discontiguous memory regions:

```cpp
template<ConstBufferSequence Buffers>
size_t send(const Buffers& buffers);  // maps to writev()
```

### Customization Points

Users should be able to specialize buffer operations for their types. Common patterns include:

**Consuming buffers** — tracking progress through a buffer sequence as bytes are sent or received:

```cpp
consuming_buffers<ConstBufferSequence> bufs(original);
while (buffer_size(bufs) > 0) {
    auto n = co_await sock.write_some(bufs);
    bufs.consume(n);  // advance past sent bytes
}
```

**Prefix extraction** — limiting work per I/O operation to bound latency or enforce policies:

```cpp
// Send at most 16KB per operation
auto chunk = buffer_prefix(16384, large_buffer_sequence);
co_await sock.write(chunk);
```

**Concatenation** — attaching protocol headers to payloads without copying:

```cpp
// HTTP: prepend header to body
auto msg = buffer_cat(header_buffers, body_buffers);
co_await sock.write(msg);  // single writev()

// WebSocket: prepend frame header to payload
auto frame = buffer_cat(frame_header, payload);
co_await sock.write(frame);
```

**Custom types** — extending the buffer vocabulary to user-defined containers:

```cpp
// Custom size computation for a rope data structure
std::size_t tag_invoke(size_tag, rope const& r) noexcept {
    return r.total_bytes();
}
```

## 3. Ranges Get Us Partway There

The `std::ranges` library provides powerful abstractions for generic sequence processing. Buffer sequences are, in fact, ranges—specifically `bidirectional_range`—and our proposal builds on this foundation. However, the value type and associated algorithms require departures optimized for buffered I/O.

### Ranges Give Wrong Answers

Consider a buffer sequence containing three buffers of 100 bytes each:

```cpp
std::array<const_buffer, 3> buffers = {...};  // 3 buffers, 100 bytes each

std::ranges::size(buffers);  // returns 3 (number of buffers)
buffer_size(buffers);        // returns 300 (total bytes)
```

The range abstraction gives you the Lebesgue measure—the count of disjoint intervals—not the total byte count that I/O operations actually need. A "buffer range" fundamentally mismodels the problem domain.

### Buffers Are Memory-Oriented

Buffer operations work with contiguous memory regions:

```cpp
std::memcpy(dest.data(), src.data(), src.size());  // entire region
```

The fundamental operation is not "iterate over bytes" but "copy this memory block." Buffer algorithms like `buffer_copy` must handle scatter/gather by iterating over *buffers*, then using `memcpy` on each contiguous region—not by iterating over individual bytes.

### Performance Implications

Consider copying 1MB across a buffer sequence:

- **Range-based**: 1,048,576 iterator increments and byte assignments
- **Buffer-based**: A handful of `memcpy` calls on contiguous regions

The buffer approach maps directly to optimized memory operations that modern CPUs and operating systems are designed for. Treating buffers as ranges of bytes would sacrifice this efficiency for an abstraction that doesn't match the problem domain.

### OS Primitives Expect Pointers

System calls like `writev`, `readv`, and `sendmsg` accept arrays of pointer+size pairs—not iterators. Buffer concepts provide a direct mapping:

```cpp
// Buffer sequence maps directly to iovec array
std::vector<iovec> to_iovec(ConstBufferSequence auto const& buffers) {
    std::vector<iovec> result;
    for (auto buf : buffers)
        result.push_back({const_cast<void*>(buf.data()), buf.size()});
    return result;
}
```

Ranges would require extracting pointers and sizes from iterators—losing the direct correspondence that makes buffer concepts efficient.

### What About `contiguous_range`?

C++20 provides `std::ranges::contiguous_range`, which guarantees elements are stored contiguously and provides `std::ranges::data()`. However, this doesn't help:

```cpp
std::array<const_buffer, 3> seq;  // satisfies contiguous_range

std::ranges::data(seq);  // pointer to first const_buffer, not first byte
```

The concept tells you the *buffer descriptors* are contiguous in memory—not that the *bytes they describe* form a contiguous region. A buffer sequence is inherently a two-level structure: a sequence of contiguous regions that are themselves scattered in memory. No single-level range concept can capture this.

### What About Range of Contiguous Ranges?

One might propose modeling buffer sequences as `range<contiguous_range<byte>>`. Several problems emerge:

**Heterogeneous composition fails.** Buffer sequences often combine different types:

```cpp
std::array<const_buffer, 2> headers;
std::span<const_buffer> body;
auto combined = buffer_cat(headers, body);  // what's the element type?
```

The result is a tuple-like view. Ranges require a single `value_type`, but `buffer_cat` produces compile-time heterogeneous sequences that avoid allocation precisely because they don't need a common container type.

**Algorithms don't compose.** Range algorithms are element-oriented:

```cpp
std::ranges::copy(src, dest);  // copies elements one by one
```

Buffer algorithms are region-oriented:

```cpp
buffer_copy(dest, src);  // memcpy per contiguous region
```

For 1MB of data, `std::ranges::copy` means 1,048,576 iterator increments. Buffer copy means a handful of `memcpy` calls.

**OS interfaces require materialization.** `writev()` expects a contiguous array of `iovec`. A `range<contiguous_range<byte>>` must be materialized:

```cpp
std::vector<iovec> vec;
for (auto inner : outer_range)
    vec.push_back({std::ranges::data(inner), std::ranges::size(inner)});
writev(fd, vec.data(), vec.size());  // allocation!
```

Buffer sequences like `std::array<const_buffer, N>` map directly to `iovec` arrays without allocation.

### The Abstraction Levels Are Inverted

The fundamental issue is that ranges and buffers have inverted mental models:

- **Ranges say**: "I'm a sequence of elements; iterate me."
- **Buffers say**: "I'm a collection of memory regions; here are pointers and sizes."

The fundamental operation on a buffer isn't "give me the next byte"—it's "give me a pointer to a contiguous region I can pass to `memcpy`, `writev`, or SIMD instructions."

### Range Algorithms Can't Shrink Elements

Range algorithms operate on whole elements—`std::views::drop(n)` drops `n` complete elements from the sequence. But buffer operations often need to *shrink* an element, not just drop it:

```cpp
// Buffer sequence: [100 bytes, 100 bytes, 100 bytes]
// Consume 50 bytes...

std::views::drop(bufs, 1);  // drops entire first buffer → 200 bytes remain
buffer_consume(bufs, 50);   // shrinks first buffer → 250 bytes remain
```

Operations like `buffer_consume`, `buffer_prefix`, and partial reads require modifying the *interior* of the first or last buffer—advancing the data pointer, reducing the size. Range algorithms cannot express this; they can only add or remove whole elements.

### What Ranges Do Provide

Our proposal embraces ranges where they fit. A buffer sequence *is* a `bidirectional_range` of buffer descriptors—we iterate forward and backward over the sequence of buffers, and range-based for loops work naturally:

```cpp
for (auto buf : buffer_sequence)
    process(buf.data(), buf.size());
```

The divergence is at the value type. Each element isn't a byte to be iterated; it's a memory region descriptor exposing `data()` and `size()`. Buffer algorithms like `buffer_size`, `buffer_copy`, and `buffer_cat` are buffer-specific precisely because range algorithms give wrong answers or wrong semantics for this domain.

Ranges get us partway there. The rest requires abstractions designed for I/O.

## 4. Buffer Types

### `mutable_buffer`

A lightweight descriptor for a contiguous region of modifiable memory:

```cpp
class mutable_buffer
{
public:
    mutable_buffer() = default;
    mutable_buffer(mutable_buffer const&) = default;
    mutable_buffer& operator=(mutable_buffer const&) = default;

    constexpr mutable_buffer(void* data, std::size_t size) noexcept;

    constexpr void* data() const noexcept;
    constexpr std::size_t size() const noexcept;

    // Advance the buffer, consuming n bytes from the front
    mutable_buffer& operator+=(std::size_t n) noexcept;
};
```

### `const_buffer`

A lightweight descriptor for a contiguous region of immutable memory:

```cpp
class const_buffer
{
public:
    const_buffer() = default;
    const_buffer(const_buffer const&) = default;
    const_buffer& operator=(const_buffer const&) = default;

    constexpr const_buffer(void const* data, std::size_t size) noexcept;
    constexpr const_buffer(mutable_buffer const& b) noexcept;  // implicit conversion

    constexpr void const* data() const noexcept;
    constexpr std::size_t size() const noexcept;

    const_buffer& operator+=(std::size_t n) noexcept;
};
```

### Why Not `span<byte>`?

The buffer types differ from `span<std::byte>` in critical ways:

1. **Type-agnostic pointers**: `void*` and `void const*` make no semantic claim about contents, matching POSIX `iovec` semantics

2. **Implicit convertibility**: `mutable_buffer` converts to `const_buffer`, enabling functions accepting `ConstBufferSequence` to work with mutable data

3. **Customizable slicing**: The `tag_invoke(slice_tag, ...)` customization point enables user-defined slicing behavior

### Why Not `pair<void*, size_t>`?

Custom buffer types enable standard library implementations to offer additional features. Microsoft provides "checked iterators" for its containers in debug builds—additional runtime validation that catches buffer overruns and iterator misuse. Similarly, an implementation could offer "checked buffers" with debug-mode bounds verification.

Constraining the fundamental buffer type to `pair` or `span` prevents this extensibility. With dedicated `const_buffer` and `mutable_buffer` types, implementations are free to add debug instrumentation, sanitizer integration, or other quality-of-implementation features without changing the public interface.

### Customization via `tag_invoke`

The buffer algorithms use `tag_invoke` ([P1895](https://wg21.link/p1895), Eric Niebler) for customization. This mechanism uses empty tag types to identify operations, with argument-dependent lookup selecting the appropriate overload:

```cpp
// Tag types identify operations
struct size_tag {};
struct slice_tag {};

enum class slice_how {
    remove_prefix,  // trim from the front
    keep_prefix     // keep only the front
};
```

The foundation types provide `tag_invoke` overloads:

```cpp
// Slice customization for const_buffer
void tag_invoke(slice_tag const&, const_buffer& b, 
                slice_how how, std::size_t n) noexcept {
    n = (std::min)(n, b.size());
    if (how == slice_how::remove_prefix)
        b += n;  // advance past n bytes
    else
        b = const_buffer(b.data(), n);  // keep only first n bytes
}

// Same patterns for mutable_buffer
```

This enables `buffer_size()`, `buffer_consume()`, `buffer_prefix()`, and similar operations to work directly on the foundation types. User-defined buffer types can provide their own `tag_invoke` overloads to participate in these algorithms.

**Design note**: The `slice_tag` customization uses a single tag with a `slice_how` discriminator rather than separate tags for each operation. This ensures that if a user customizes slicing for their type, they must handle *all* slice operations in one overload—preventing irregular types where `remove_prefix` works but `keep_prefix` doesn't.

**Note on `tag_invoke`**: [P1895](https://wg21.link/p1895) was accepted into C++23 working drafts but removed before standardization—falling out of favor in a single release cycle. Nevertheless, it remains a practical customization mechanism for library design, and its pattern influenced the eventual direction of customization points in C++.

## 5. Buffer Sequences

Alexander Stepanov's founding insight for the STL was that algorithms should be parameterized on *concepts*, not concrete types. `std::sort` doesn't accept `std::vector<T>&`—it accepts any random-access iterator range. This single design decision enabled one algorithm to work with vectors, arrays, deques, and user-defined containers alike.

Buffer sequences follow the same principle. Rather than defining I/O operations in terms of concrete types like `span<span<byte>>`, we define them in terms of what the type *can do*: iterate bidirectionally over memory region descriptors. Buffer sequences are a generalization of the POSIX `iovec` array, elevated to a concept that permits zero-allocation composition.

A type models `ConstBufferSequence` if it represents one or more contiguous memory regions for reading. A type models `MutableBufferSequence` if those regions are writable. The concept doesn't care whether you're passing a single buffer, a fixed array, a dynamic vector, or a custom rope—it only requires the operations that I/O algorithms need.

The definitions that follow are identical to those in the Networking TS ([N4771](https://wg21.link/n4771)). We have no shame in copying that which works.

### `ConstBufferSequence`

A type satisfies `ConstBufferSequence` if it is convertible to `const_buffer`, or if it is a bidirectional range whose value type is convertible to `const_buffer`:

```cpp
template<typename T>
concept ConstBufferSequence =
    std::is_convertible_v<T, const_buffer> || (
        std::ranges::bidirectional_range<T> &&
        std::is_convertible_v<std::ranges::range_value_t<T>, const_buffer>);
```

This definition accepts:

- A single `const_buffer` (treated as a one-element sequence)
- A `std::array<const_buffer, N>` (fixed-size sequence)
- A `std::vector<const_buffer>` (dynamic sequence)
- Any user-defined type modeling the concept

### `MutableBufferSequence`

The mutable counterpart:

```cpp
template<typename T>
concept MutableBufferSequence =
    std::is_convertible_v<T, mutable_buffer> || (
        std::ranges::bidirectional_range<T> &&
        std::is_convertible_v<std::ranges::range_value_t<T>, mutable_buffer>);
```

## 6. Buffer Algorithms

### `buffer_size`

Returns the total number of bytes across all buffers in a sequence:

```cpp
template<ConstBufferSequence CB>
constexpr std::size_t buffer_size(CB const& bs) noexcept;
```

This differs from `std::ranges::size()`, which returns the number of elements. For a sequence of three 100-byte buffers, `buffer_size()` returns 300. The default implementation iterates through the sequence summing individual buffer sizes. User-defined buffer sequences can provide a `tag_invoke(size_tag, ...)` overload for O(1) computation when size is cached.

### `buffer_empty`

Checks whether a buffer sequence contains any data:

```cpp
template<ConstBufferSequence CB>
constexpr bool buffer_empty(CB const& bs) noexcept;
```

A sequence is empty if all constituent buffers have size zero, or if the sequence contains no buffers. This function exists because checking emptiness is generally faster than computing `buffer_size() == 0`. For large buffer sequences, `buffer_empty` can short-circuit on the first non-empty buffer rather than summing all sizes.

### `buffer_copy`

Copies bytes from one buffer sequence to another:

```cpp
template<MutableBufferSequence Dest, ConstBufferSequence Src>
std::size_t buffer_copy(
    Dest const& dest,
    Src const& src,
    std::size_t at_most = std::size_t(-1)) noexcept;
```

Returns the number of bytes copied, which equals `min(buffer_size(dest), buffer_size(src), at_most)`. This function handles the complexity of iterating through discontiguous source and destination regions.

### `std::begin` / `std::end` Overloads

To treat single buffers as one-element sequences, we provide `std::begin` and `std::end` overloads for the buffer types:

```cpp
namespace std {
    const_buffer* begin(const_buffer& b) noexcept { return &b; }
    const_buffer* end(const_buffer& b) noexcept { return &b + 1; }
    
    mutable_buffer* begin(mutable_buffer& b) noexcept { return &b; }
    mutable_buffer* end(mutable_buffer& b) noexcept { return &b + 1; }
}
```

This enables uniform iteration regardless of whether a function receives a single buffer or a sequence—`std::ranges::begin`/`end` and range-for loops just work. Buffer sequences that are already ranges (like `std::array<const_buffer, N>`) need no special handling.

### `buffer_type`

A metafunction returning the appropriate buffer type for a sequence:

```cpp
template<typename BS>
using buffer_type = std::conditional_t<
    MutableBufferSequence<BS>,
    mutable_buffer, const_buffer>;
```

## 7. Customization Points

### `tag_invoke` Protocol

The design uses Eric Niebler's `tag_invoke` ([P1895](https://wg21.link/p1895)) for extensibility, enabling users to customize behavior for their types without modifying the library.

### `size_tag`

Customizes `buffer_size()` for user-defined types:

```cpp
struct size_tag {};

// Default implementation iterates and sums
template<ConstBufferSequence CB>
std::size_t tag_invoke(size_tag const&, CB const& bs) noexcept {
    std::size_t n = 0;
    for(auto it = begin(bs); it != end(bs); ++it)
        n += const_buffer(*it).size();
    return n;
}

// User customization for O(1) size
std::size_t tag_invoke(size_tag const&, my_rope const& r) noexcept {
    return r.cached_size();  // O(1) instead of O(n)
}
```

### `slice_tag`

Customizes buffer slicing operations:

```cpp
struct slice_tag {};

enum class slice_how {
    remove_prefix,  // trim from the front
    keep_prefix     // keep only the front
};

// Customize slicing for buffer types
void tag_invoke(
    slice_tag const&,
    const_buffer& b,
    slice_how how,
    std::size_t n) noexcept;
```

This enables efficient slicing of buffer sequences without copying. The `remove_prefix` operation advances the start; `keep_prefix` truncates to the first `n` bytes.

### Buffer Pairs

For the common case of two-buffer scatter/gather (e.g., header + body), the library provides convenient type aliases:

```cpp
using const_buffer_pair = std::array<const_buffer, 2>;
using mutable_buffer_pair = std::array<mutable_buffer, 2>;
```

These satisfy `ConstBufferSequence` and `MutableBufferSequence` respectively, with specialized `tag_invoke(slice_tag, ...)` overloads for efficient slicing that can shrink individual buffers within the pair.

## 8. Implementation Experience

Asio gets buffers mostly right. The buffer concepts proposed here derive from Christopher Kohlhoff's Boost.Asio and its standardization effort, the Networking TS ([N4771](https://wg21.link/n4771)), which have:

- **Twenty years** of production deployment
- **Thousands** of projects using the buffer model
- **Proven** mapping to OS scatter/gather primitives
- **Battle-tested** edge cases and error handling

The concepts formalize what Asio demonstrated pragmatically: that buffer sequences enable zero-allocation composition while concrete spans serve type-erasure boundaries.

Notable adopters include:

- Boost.Beast (HTTP/WebSocket)
- Boost.MySQL
- Boost.Redis
- Numerous proprietary networking stacks

This follows the precedent of Alexander Stepanov's STL: concepts proven through extensive real-world use before standardization. Just as STL's iterator concepts emerged from practical generic programming experience, the buffer concepts here emerged from two decades of network I/O practice.

The Boost.Capy library (https://github.com/cppalliance/capy) demonstrates that this model can interoperate transparently with Asio without requiring Asio headers or dependencies—a quality of implementation detail that validates the design's compatibility.

## 9. Comparison with Alternatives

### `std::span<std::byte>`

| Aspect | `span<byte>` | Buffer Concepts |
|--------|--------------|-----------------|
| Composition | Requires allocation | Zero-allocation |
| Scatter/gather | Homogeneous only | Heterogeneous |
| Semantics | Imposes `std::byte` | Type-agnostic |
| Extensibility | None | `tag_invoke` |
| Single buffer | Native | Via convertibility |

### Raw `void*` + `size_t`

| Aspect | Raw pointers | Buffer Concepts |
|--------|--------------|-----------------|
| Type safety | None | Strongly typed |
| Generic programming | Impossible | Full support |
| Composition | Manual | Automatic |
| Const-correctness | Manual | Enforced |

### `std::ranges`

Ranges cannot express buffer composition efficiently:

```cpp
// No views::concat until C++26
// views::join requires homogeneous element types
auto mixed = std::views::join(std::array{string_view, span<byte>});  // error
```

Buffer concepts accepted heterogeneous sequences in 2003.

---

## 10. Conclusion

The buffer concepts proposed here occupy a pragmatic middle ground:

- **More abstract than spans**: Enabling composition and user extension
- **More concrete than ranges**: Mapping directly to OS primitives
- **Grounded in practice**: Twenty years of Asio deployment

The core insight is that I/O buffers are not just byte arrays—they are a semantic concept requiring:

1. Type-agnostic memory description
2. Composable sequences for scatter/gather
3. Customization points for user types
4. Efficient mapping to system calls

`std::span<std::byte>` provides none of these. The buffer concepts provide all of them, with decades of production validation.

## 11. Proposed Wording

The wording below is provided not primarily to advocate for standardization, but to demonstrate that this proposal is eminently implementable and represents a minimal addition to the standard library. The entire surface area consists of two lightweight classes and two concepts.

### Header `<buffer>` synopsis

```cpp
namespace std {

// Buffer types
class mutable_buffer;
class const_buffer;

// Buffer concepts
template<typename T>
concept MutableBufferSequence = /* see below */;

template<typename T>
concept ConstBufferSequence = /* see below */;

// Buffer algorithms
template<ConstBufferSequence CB>
constexpr size_t buffer_size(CB const& buffers) noexcept;

template<ConstBufferSequence CB>
constexpr bool buffer_empty(CB const& buffers) noexcept;

template<MutableBufferSequence Dest, ConstBufferSequence Src>
size_t buffer_copy(Dest const& dest, Src const& src,
                   size_t max_size = size_t(-1)) noexcept;

// Buffer sequence iteration
template<ConstBufferSequence BS>
constexpr auto begin(BS const& buffers) noexcept;

template<ConstBufferSequence BS>
constexpr auto end(BS const& buffers) noexcept;

// Buffer type metafunction
template<typename BS>
using buffer_type = conditional_t<MutableBufferSequence<BS>,
                                  mutable_buffer, const_buffer>;

} // namespace std
```

### Class `mutable_buffer`

```cpp
namespace std {

class mutable_buffer {
    void* data_ = nullptr;
    size_t size_ = 0;

public:
    mutable_buffer() = default;
    mutable_buffer(mutable_buffer const&) = default;
    mutable_buffer& operator=(mutable_buffer const&) = default;

    constexpr mutable_buffer(void* p, size_t n) noexcept
        : data_(p), size_(n) {}

    constexpr void* data() const noexcept { return data_; }
    constexpr size_t size() const noexcept { return size_; }

    mutable_buffer& operator+=(size_t n) noexcept {
        size_t k = n < size_ ? n : size_;
        data_ = static_cast<char*>(data_) + k;
        size_ -= k;
        return *this;
    }
};

} // namespace std
```

### Class `const_buffer`

```cpp
namespace std {

class const_buffer {
    void const* data_ = nullptr;
    size_t size_ = 0;

public:
    const_buffer() = default;
    const_buffer(const_buffer const&) = default;
    const_buffer& operator=(const_buffer const&) = default;

    constexpr const_buffer(void const* p, size_t n) noexcept
        : data_(p), size_(n) {}

    constexpr const_buffer(mutable_buffer const& b) noexcept
        : data_(b.data()), size_(b.size()) {}

    constexpr void const* data() const noexcept { return data_; }
    constexpr size_t size() const noexcept { return size_; }

    const_buffer& operator+=(size_t n) noexcept {
        size_t k = n < size_ ? n : size_;
        data_ = static_cast<char const*>(data_) + k;
        size_ -= k;
        return *this;
    }
};

} // namespace std
```
