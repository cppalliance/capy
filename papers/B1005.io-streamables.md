# IoStreamables: Coroutine Driven Streams

## Abstract

This paper proposes six concepts for coroutine-driven I/O streams and their type-erasing wrappers. The concepts form a three-tier hierarchy: streams for partial I/O operations, sources and sinks for complete transfers, and buffer variants for zero-copy patterns. All operations return awaitables satisfying the _IoAwaitable_ protocol (BOOST1000), enabling forward propagation of execution context through coroutine chains.

The type-erasing wrappers provide an ABI firewall between algorithms and transport implementations. This design enables the C++ standards committee to standardize abstract stream interfaces while leaving security-critical transport implementations (TLS, platform sockets) to the ecosystem—a division of labor aligned with the committee's institutional strengths.

Working implementations exist in Boost.Capy, Boost.Corosio, Boost.HTTP, and Boost.Beast2.

---

## 1. Motivation

### 1.1 The Standardization Challenge

The C++ standards committee excels at consensus-building for stable, well-understood domains. Abstract interfaces, concepts, generic algorithms, and vocabulary types emerge successfully from the multi-meeting proposal process. However, the committee's bureaucratic structure creates tensions when applied to security-critical, fast-moving targets.

Three-year release cycles create deadline pressure. "Get it in before the cutoff" incentivizes premature standardization rather than patient vetting. The result is an institution that moves slowly when speed is needed (security vulnerabilities) and rushes when patience is needed (design maturity).

Security vulnerabilities demand immediate response—days, not years. TLS libraries like OpenSSL and WolfSSL patch CVEs within weeks. The C++ memory safety crisis demonstrates the committee's structural inability to respond quickly to external pressure. If a hypothetical `std::socket` uses OpenSSL internally, a critical vulnerability creates impossible choices:

- Ship broken standard library implementations, OR
- Break ABI to update OpenSSL

The committee lacks executive potency for security-critical, fast-moving targets. Standardizing concrete transport types creates a long-term maintenance burden that compounds with each vulnerability disclosure.

### 1.2 The IoStreamables Solution

IoStreamables address this challenge through type erasure. Algorithms operate on `any_stream`, `any_source`, and `any_sink`—with no visibility of underlying transport types. This creates an ABI firewall:

- Changing the TLS implementation doesn't break algorithm ABI
- Security updates don't require recompilation of algorithm code
- Vendors can ship proprietary TLS integrations without exposing internals
- Implementation defects stay contained within ecosystem libraries, not the standard

The division of labor aligns with institutional capability:

| Committee standardizes | Ecosystem provides |
|------------------------|-------------------|
| Concepts (`ReadStream`, `WriteSink`, etc.) | Sockets |
| Type-erasing wrappers | TLS streams |
| Generic algorithms | File handles |
| Buffer vocabulary types | Platform-specific transports |

This follows the `std::pmr::memory_resource` precedent: abstract interface in the standard, allocator implementations outside.

### 1.3 Why Three Tiers?

Different use cases require different abstraction levels:

**Streams** (`ReadStream`, `WriteStream`) provide fine-grained control with partial I/O operations. A `read_some` call may return fewer bytes than requested—the caller loops until satisfied. This matches socket semantics and enables efficient buffer management when the application controls chunking.

**Sources and Sinks** (`ReadSource`, `WriteSink`) provide complete transfers. A `read` call fills the entire buffer or fails. A `write` call consumes all bytes. This abstraction suits HTTP body processing where the protocol layer handles framing and the application wants complete messages.

**Buffer Sources and Sinks** (`BufferSource`, `BufferSink`) enable zero-copy patterns. Rather than the caller providing buffers, the callee provides buffer descriptors from internal storage. The caller writes directly into sink buffers or reads directly from source buffers. This is essential for compression, encryption, and transformation pipelines where intermediate buffering would double memory traffic.

## 2. Concept Definitions

All concepts require operations returning awaitables that satisfy _IoAwaitable_ (BOOST1000). Return values decompose via structured bindings to `(error_code, ...)` tuples.

### 2.1 ReadStream

A type satisfies `ReadStream` if it provides a `read_some` member function template accepting any `MutableBufferSequence` (BOOST1004):

```cpp
template<typename T>
concept ReadStream =
    requires(T& stream, mutable_buffer_archetype buffers)
    {
        { stream.read_some(buffers) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(stream.read_some(buffers)),
            system::error_code, std::size_t>;
    };
```

**Semantic requirements:**

Attempts to read up to `buffer_size(buffers)` bytes from the stream into the buffer sequence.

If `buffer_size(buffers) > 0`:

- If `!ec`, then `n >= 1 && n <= buffer_size(buffers)`. `n` bytes were read into the buffer sequence.
- If `ec`, then `n >= 0 && n <= buffer_size(buffers)`. `n` is the number of bytes read before the I/O condition arose.

If `buffer_empty(buffers)` is `true`, `n` is 0. The empty buffer is not itself a cause for error, but `ec` may reflect the state of the stream.

### 2.2 WriteStream

A type satisfies `WriteStream` if it provides a `write_some` member function template accepting any `ConstBufferSequence`:

```cpp
template<typename T>
concept WriteStream =
    requires(T& stream, const_buffer_archetype buffers)
    {
        { stream.write_some(buffers) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(stream.write_some(buffers)),
            system::error_code, std::size_t>;
    };
```

**Semantic requirements:**

Attempts to write up to `buffer_size(buffers)` bytes from the buffer sequence to the stream.

If `buffer_size(buffers) > 0`:

- If `!ec`, then `n >= 1 && n <= buffer_size(buffers)`. `n` bytes were written from the buffer sequence.
- If `ec`, then `n >= 0 && n <= buffer_size(buffers)`. `n` is the number of bytes written before the I/O condition arose.

If `buffer_empty(buffers)` is `true`, `n` is 0. The empty buffer is not itself a cause for error, but `ec` may reflect the state of the stream. The caller must loop to write remaining data.

### 2.3 ReadSource

A type satisfies `ReadSource` if it provides a `read` member function template that fills the entire buffer sequence:

```cpp
template<typename T>
concept ReadSource =
    requires(T& source, mutable_buffer_archetype buffers)
    {
        { source.read(buffers) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(source.read(buffers)),
            system::error_code, std::size_t>;
    };
```

**Semantic requirements:**

On success, `n == buffer_size(buffers)`. Partial reads are not permitted—the operation either fills the buffer completely or fails.

### 2.4 WriteSink

A type satisfies `WriteSink` if it provides `write` and `write_eof` operations:

```cpp
template<typename T>
concept WriteSink =
    requires(T& sink, const_buffer_archetype buffers, bool eof)
    {
        { sink.write(buffers) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(sink.write(buffers)),
            system::error_code, std::size_t>;
        { sink.write(buffers, eof) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(sink.write(buffers, eof)),
            system::error_code, std::size_t>;
        { sink.write_eof() } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(sink.write_eof()),
            system::error_code>;
    };
```

**Semantic requirements:**

The `write` operation consumes all bytes from the buffer sequence. The `write(buffers, eof)` overload combines data writing with end-of-stream signaling when `eof` is `true`. The `write_eof` operation finalizes the sink—no further writes are permitted after successful completion.

The EOF protocol is essential for sinks that must signal completion to downstream consumers (e.g., HTTP chunked encoding, compression stream finalization).

### 2.5 BufferSource

A type satisfies `BufferSource` if it provides `pull` and `consume` operations:

```cpp
template<typename T>
concept BufferSource =
    requires(T& src, const_buffer* arr, std::size_t max_count, std::size_t n)
    {
        { src.pull(arr, max_count) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(src.pull(arr, max_count)),
            system::error_code, std::size_t>;
        src.consume(n);
    };
```

**Semantic requirements:**

The `pull` operation fills the provided buffer descriptor array with data from internal storage. On return:

- **Data available**: `!ec` and `count > 0`. The array contains `count` buffer descriptors.
- **Source exhausted**: `!ec` and `count == 0`. The transfer is complete.
- **Error**: `ec`.

Calling `pull` multiple times without intervening `consume` returns the same unconsumed data. The `consume(n)` operation advances the read position by `n` bytes. The next `pull` returns data starting after the consumed bytes.

Buffer descriptors remain valid until the next call to `pull`, `consume`, or source destruction.

### 2.6 BufferSink

A type satisfies `BufferSink` if it provides `prepare`, `commit`, and `commit_eof` operations:

```cpp
template<typename T>
concept BufferSink =
    requires(T& sink, mutable_buffer* arr, std::size_t max_count, std::size_t n, bool eof)
    {
        { sink.prepare(arr, max_count) } -> std::convertible_to<std::size_t>;
        { sink.commit(n) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(sink.commit(n)),
            system::error_code>;
        { sink.commit(n, eof) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(sink.commit(n, eof)),
            system::error_code>;
        { sink.commit_eof() } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(sink.commit_eof()),
            system::error_code>;
    };
```

**Semantic requirements:**

The `prepare` operation (synchronous) fills the provided buffer descriptor array with writable regions from internal storage, returning the count of valid descriptors. The caller writes data directly into these buffers.

The `commit(n)` operation (asynchronous) finalizes `n` bytes of written data. The `commit(n, eof)` overload combines commit with end-of-stream signaling. The `commit_eof()` operation finalizes the sink without additional data.

## 3. Type-Erasing Wrappers

The library provides type-erasing wrappers for each concept:

| Wrapper | Concept | Notes |
|---------|---------|-------|
| `any_read_stream` | `ReadStream` | |
| `any_write_stream` | `WriteStream` | |
| `any_stream` | Both | Inherits from both wrappers |
| `any_read_source` | `ReadSource` | |
| `any_write_sink` | `WriteSink` | |
| `any_buffer_source` | `BufferSource` | Also satisfies `ReadSource` via copy |
| `any_buffer_sink` | `BufferSink` | Also satisfies `WriteSink` via copy |

### 3.1 Design

All wrappers share a common implementation pattern:

```cpp
class any_read_stream
{
    void* stream_ = nullptr;           // Pointer to wrapped object
    vtable const* vt_ = nullptr;       // Type-specific dispatch table
    void* cached_frame_ = nullptr;     // Preallocated coroutine frame
    std::size_t cached_size_ = 0;      // Frame size

public:
    template<ReadStream S>
        requires (!std::same_as<std::decay_t<S>, any_read_stream>)
    any_read_stream(S& s) noexcept;

    template<MutableBufferSequence MB>
    auto read_some(MB buffers);  // Returns awaitable
};
```

**Reference semantics:** Wrappers hold a pointer to the wrapped object without taking ownership. The wrapped object must outlive the wrapper.

**Frame preallocation:** The constructor preallocates the internal coroutine frame. This reserves all virtual address space at server startup, enabling upfront memory budgeting rather than piecemeal allocation as traffic arrives.

**Vtable dispatch:** Each wrapped type gets a compile-time vtable. Operations dispatch through function pointers, with the implementation casting `void*` back to the concrete type.

**Zero steady-state allocation:** Custom `operator new` in the internal coroutine's promise type uses the cached frame. After construction, operations allocate nothing.

### 3.2 Example

```cpp
socket sock(ioc);
any_read_stream stream(sock);

mutable_buffer buf(data, size);
auto [ec, n] = co_await stream.read_some(std::span(&buf, 1));
```

The algorithm sees only `any_read_stream`—the socket type is erased. Changing from `socket` to `tls_stream` requires no recompilation of algorithm code.

## 4. Algorithms

The library provides composing algorithms that operate on the stream, source, and sink concepts. These algorithms demonstrate the power of concept-based generic programming—they work with any conforming type, including the type-erasing wrappers.

### 4.1 Transfer Algorithms

**`push_to`** transfers data from a `BufferSource` to either a `WriteSink` or `WriteStream`:

```cpp
template<BufferSource Src, WriteSink Sink>
io_task<std::size_t>
push_to(Src& source, Sink& sink);

template<BufferSource Src, WriteStream Stream>
io_task<std::size_t>
push_to(Src& source, Stream& stream);
```

The function pulls data from the source and writes it to the destination until the source is exhausted. When writing to a `WriteSink`, `write_eof()` is called to finalize the transfer. Returns the total bytes transferred.

**`pull_from`** transfers data from a `ReadSource` or `ReadStream` to a `BufferSink`:

```cpp
template<ReadSource Src, BufferSink Sink>
io_task<std::size_t>
pull_from(Src& source, Sink& sink);

template<ReadStream Src, BufferSink Sink>
io_task<std::size_t>
pull_from(Src& source, Sink& sink);
```

The function uses the callee-owns-buffers model: the sink provides writable buffers via `prepare()`, the source reads directly into them, and the sink commits the data. When the source signals EOF, `commit_eof()` finalizes the sink.

### 4.2 Completion Algorithms

**`read`** reads from a `ReadStream` until a buffer sequence is filled:

```cpp
auto read(
    ReadStream auto& stream,
    MutableBufferSequence auto const& buffers) ->
        io_task<std::size_t>;
```

Loops calling `read_some()` until the entire buffer sequence is filled or an error occurs. This converts partial-read semantics into complete-read semantics.

**`read`** (dynamic buffer overload) reads from a `ReadSource` into a growing buffer:

```cpp
auto read(
    ReadSource auto& source,
    DynamicBufferParam auto&& buffers,
    std::size_t initial_amount = 2048) ->
        io_task<std::size_t>;
```

Reads until EOF, growing the buffer using a 1.5x growth strategy. Useful for reading complete responses of unknown size.

**`write`** writes a buffer sequence to a `WriteStream`:

```cpp
auto write(
    WriteStream auto& stream,
    ConstBufferSequence auto const& buffers) ->
        io_task<std::size_t>;
```

Loops calling `write_some()` until the entire buffer sequence is written or an error occurs.

### 4.3 Algorithm Composition

These algorithms compose naturally:

```cpp
// Transfer HTTP body from source to compressed sink
task<> compress_body(BufferSource auto& body, BufferSink auto& compressed)
{
    zlib_sink compressor(compressed);
    auto [ec, n] = co_await push_to(body, compressor);
}

// Read entire response into string
task<std::string> fetch_body(ReadSource auto& source)
{
    std::string result;
    auto [ec, n] = co_await read(source, string_buffers(result));
    return result;
}
```

## 5. Design Rationale

### 5.1 Partial vs Complete Operations

Streams provide `read_some`/`write_some` (partial); sources and sinks provide `read`/`write` (complete). Both are necessary:

**Partial operations** give the caller control over chunking. A protocol parser may want to read exactly as much as needed for the next frame header, avoiding over-read that would require buffering.

**Complete operations** simplify application code. An HTTP body consumer wants complete chunks without manual looping. The source/sink abstracts the complexity of reassembling partial reads.

### 5.2 The EOF Protocol

Sinks require explicit EOF signaling because many protocols need to distinguish "more data coming" from "transfer complete":

- HTTP chunked encoding requires a zero-length chunk to signal end
- Compression streams must flush final blocks
- TLS requires close-notify alerts

The `write_eof()` operation and `write(buffers, true)` overload provide this signaling.

### 5.3 Buffer Lifetime

For streams and sources/sinks, the caller provides buffers. The caller must ensure buffer validity until the `co_await` expression returns.

For buffer sources and sinks, the callee provides buffer descriptors. These remain valid until the next operation or object destruction. This enables zero-copy: the caller writes directly into the sink's internal buffers without intermediate copies.

### 5.4 Integration with IoAwaitable

All operations return awaitables satisfying _IoAwaitable_ (BOOST1000). This enables:

- **Forward context propagation**: Executor, stop token, and allocator flow through `await_transform`
- **Symmetric transfer**: Coroutine handles transfer directly without stack growth
- **Cancellation**: Stop tokens propagate to the lowest-level I/O operation

## 6. Strategic Implications for Standardization

### 6.1 Playing to Institutional Strengths

The IoStreamables design aligns standardization scope with the committee's demonstrated capabilities:

**WG21 excels at:**
- Abstract interfaces and concepts
- Generic algorithms
- Vocabulary types with stable ABI

**WG21 struggles with:**
- Security-critical implementation details
- Rapid-response maintenance
- Platform-specific integration

IoStreamables enable the committee to standardize what it does well (concepts, wrappers, algorithms) while leaving what it does poorly (transport implementations) to the ecosystem.

### 6.2 The ABI Firewall

Algorithms compiled against `any_stream` never see transport implementation types:

```cpp
// This function has stable ABI regardless of transport implementation
task<std::size_t> transfer(any_read_stream& src, any_write_sink& dst);
```

When OpenSSL patches a vulnerability:
1. The ecosystem rebuilds the TLS stream implementation
2. Applications relink (or dynamically load the updated library)
3. Algorithm code requires no recompilation

Implementation defects stay contained. A bug in the TLS wrapper affects only code that uses TLS—not every algorithm that uses streams.

### 6.3 Precedent

This model has precedent in the standard library:

- `std::pmr::memory_resource` — Abstract interface standardized; allocator implementations provided by vendors and users
- `std::locale::facet` — Abstract interface for locale customization; implementations outside the standard
- `std::streambuf` — Abstract buffer interface; concrete implementations in `std::filebuf`, `std::stringbuf`, etc.

## 7. Implementation Experience

Working implementations exist across multiple libraries:

- **Boost.Capy** — Core concepts and type-erasing wrappers (https://github.com/cppalliance/capy)
- **Boost.Corosio** — Sockets, timers, signals, DNS resolution using these concepts (https://github.com/cppalliance/corosio)
- **Boost.HTTP** — HTTP protocol implementation with sources/sinks for body streaming (https://github.com/cppalliance/http)
- **Boost.Beast2** — WebSocket and HTTP built on IoStreamable abstractions (https://github.com/cppalliance/beast2)

This follows the STL precedent: concepts proven through extensive real-world use before standardization. The designs emerged from solving practical problems in production I/O code, not theoretical exercises.

### 7.1 Coroutine-Only Enables Specific Optimizations

Field experience demonstrates that going coroutine-only (not supporting callbacks) affords optimizations unavailable to dual-mode designs:

**Cached coroutine frames.** Type-erasing wrappers preallocate frames at construction. After startup, operations perform zero allocations. A callback-compatible design would need to support allocation at each operation initiation.

**Symmetric transfer.** Coroutine handles transfer directly to continuations without growing the stack. Callback dispatch requires function calls that accumulate stack frames. Deep operation chains in callback mode risk stack overflow; coroutine mode uses constant stack space.

**Structural type erasure.** Coroutine handles are already type-erased pointers—`std::coroutine_handle<void>` has the same representation regardless of promise type. The allocation we cannot avoid pays for the type erasure we need. Callbacks require separate type erasure machinery.

**Forward context propagation.** Executor, allocator, and stop token flow naturally through `await_transform`. Each suspension point injects context into child operations. Callbacks require explicit parameter threading or ambient state.

**Same-executor optimization.** When a child coroutine completes, `complete()` compares executors via pointer comparison. If they match, symmetric transfer returns directly. If they differ, dispatch through the caller's executor ensures correct affinity. This optimization is free in coroutine mode; callbacks would need additional tracking.

These optimizations compound. A callback-compatible design cannot achieve the same performance profile because it must accommodate both models. The coroutine-only constraint is a feature, not a limitation.

## 8. Usage Examples

### 8.1 Transfer Function

A generic transfer from source to sink:

```cpp
template<BufferSource Source, WriteSink Sink>
io_task<std::size_t> transfer(Source& source, Sink& sink)
{
    const_buffer arr[16];
    std::size_t total = 0;
    for(;;)
    {
        auto [ec, count] = co_await source.pull(arr, 16);
        if(ec)
            co_return {ec, total};
        if(count == 0)
        {
            auto [eof_ec] = co_await sink.write_eof();
            co_return {eof_ec, total};
        }
        auto [write_ec, n] = co_await sink.write(std::span(arr, count));
        if(write_ec)
            co_return {write_ec, total};
        source.consume(n);
        total += n;
    }
}
```

### 8.2 HTTP Body Streaming

Reading an HTTP response body through a source:

```cpp
task<> process_response(http_response& resp)
{
    any_read_source body = resp.body();  // Type-erased body source
    
    char buffer[4096];
    for(;;)
    {
        auto [ec, n] = co_await body.read(mutable_buffer(buffer, sizeof(buffer)));
        if(ec == cond::eof)
            break;
        if(ec)
            throw system_error(ec);
        process_chunk(buffer, n);
    }
}
```

### 8.3 Compression Pipeline

Chaining a compression sink:

```cpp
task<> send_compressed(any_write_sink& output, std::string_view data)
{
    zlib_sink compressor(output);  // Wraps output, satisfies WriteSink
    
    auto [ec, n] = co_await compressor.write(make_buffer(data), true);
    if(ec)
        throw system_error(ec);
}
```

### 9.2 Concept `read_stream`

```cpp
template<typename T>
concept read_stream =
    requires(T& stream, mutable_buffer_archetype buffers) {

        requires awaitable_decomposes_to<
            decltype(stream.read_some(buffers)),
            error_code, size_t>;

```

*Remarks:* A type satisfying `read_stream` provides partial read operations. The operation reads at least one byte on success, or returns an error code.

### 9.3 Concept `write_stream`

```cpp
    };
```

*Remarks:* A type satisfying `write_stream` provides partial write operations.

```cpp
template<typename T>
```

```cpp
            error_code>;
```

*Remarks:* A type satisfying `buffer_sink` provides zero-copy write operations through callee-owned buffers.

### 9.8 Class `any_read_stream`

```cpp
namespace std {

class any_read_stream {
    void* stream_;                    // exposition only
    unspecified const* vt_;           // exposition only
    void* cached_frame_;              // exposition only
    size_t cached_size_;              // exposition only

public:
    any_read_stream() = default;
    any_read_stream(any_read_stream const&) = delete;
    any_read_stream& operator=(any_read_stream const&) = delete;
    any_read_stream(any_read_stream&&) noexcept;
    any_read_stream& operator=(any_read_stream&&) noexcept;
    ~any_read_stream();

    template<read_stream S>
        requires (!same_as<decay_t<S>, any_read_stream>)
    any_read_stream(S& s) noexcept;

    bool has_value() const noexcept;
    explicit operator bool() const noexcept;

    template<mutable_buffer_sequence MB>

```

```cpp
template<read_stream S>
    requires (!same_as<decay_t<S>, any_read_stream>)
any_read_stream(S& s) noexcept;
```

*Effects:* Type-erases `s` and preallocates the internal coroutine frame. The referent must remain valid for the lifetime of `*this`.

```cpp
template<mutable_buffer_sequence MB>
unspecified read_some(MB buffers);
```

*Returns:* An awaitable that await-returns `(error_code, size_t)`.

*Effects:* Equivalent to calling `read_some(buffers)` on the wrapped stream.

---

## 10. Conclusion

IoStreamables provide a layered abstraction for coroutine-driven I/O:

1. **Streams** for partial operations with fine-grained control
2. **Sources and Sinks** for complete transfers with EOF signaling
3. **Buffer variants** for zero-copy patterns

The type-erasing wrappers create an ABI firewall between algorithms and transport implementations. This enables a division of labor: the committee standardizes abstract interfaces (its strength), while the ecosystem provides security-critical transports (where agility matters).

Field experience across Boost.Capy, Boost.Corosio, Boost.HTTP, and Boost.Beast2 demonstrates that the coroutine-only design enables specific optimizations—cached frames, symmetric transfer, structural type erasure—unavailable to dual-mode designs. The constraint is a feature.

The proposal is eminently implementable. The entire surface area consists of six concepts and seven wrapper classes, building on the _IoAwaitable_ protocol (BOOST1000) and buffer concepts (BOOST1004).
