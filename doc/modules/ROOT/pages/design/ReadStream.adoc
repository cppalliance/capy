= ReadStream Concept Design

== Overview

This document describes the design of the `ReadStream` concept: the
fundamental partial-read primitive in the concept hierarchy. It explains
why `read_some` is the correct building block, how composed algorithms
build on top of it, and the relationship to `ReadSource`.

== Definition

[source,cpp]
----
template<typename T>
concept ReadStream =
    requires(T& stream, mutable_buffer_archetype buffers)
    {
        { stream.read_some(buffers) } -> IoAwaitable;
        requires awaitable_decomposes_to<
            decltype(stream.read_some(buffers)),
            std::error_code, std::size_t>;
    };
----

A `ReadStream` provides a single operation:

=== `read_some(buffers)` -- Partial Read

Reads one or more bytes from the stream into the buffer sequence.
Returns `(error_code, std::size_t)` where `n` is the number of bytes
read.

==== Semantics

- On success: `!ec`, `n >= 1` and `n \<= buffer_size(buffers)`.
- On EOF: `ec == cond::eof`, `n == 0`.
- On error: `ec`, `n == 0`.
- If `buffer_empty(buffers)`: completes immediately, `!ec`, `n == 0`.

The caller must not assume the buffer is filled. `read_some` may
return fewer bytes than the buffer can hold. This is the defining
property of a partial-read primitive.

Buffers in the sequence are filled completely before proceeding to the
next buffer in the sequence.

==== Buffer Lifetime

The caller must ensure that the memory referenced by `buffers` remains
valid until the `co_await` expression returns.

==== Conforming Signatures

[source,cpp]
----
template<MutableBufferSequence Buffers>
IoAwaitable auto read_some(Buffers buffers);
----

Buffer sequences should be accepted by value when the member function
is a coroutine, to ensure the sequence lives in the coroutine frame
across suspension points.

== Concept Hierarchy

`ReadStream` is the base of the read-side hierarchy:

----
ReadStream    { read_some }
    |
    v
ReadSource    { read_some, read }
----

`ReadSource` refines `ReadStream`. Every `ReadSource` is a
`ReadStream`. Algorithms constrained on `ReadStream` accept both raw
streams and sources. The `ReadSource` concept adds a complete-read
primitive on top of the partial-read primitive.

This mirrors the write side:

----
WriteStream   { write_some }
    |
    v
WriteSink     { write_some, write, write_eof(buffers), write_eof() }
----

== Composed Algorithms

Three composed algorithms build on `read_some`:

=== `read(stream, buffers)` -- Fill a Buffer Sequence

[source,cpp]
----
auto read(ReadStream auto& stream,
          MutableBufferSequence auto const& buffers)
    -> io_task<std::size_t>;
----

Loops `read_some` until the entire buffer sequence is filled or an
error (including EOF) occurs. On success, `n == buffer_size(buffers)`.

[source,cpp]
----
template<ReadStream Stream>
task<> read_header(Stream& stream)
{
    char header[16];
    auto [ec, n] = co_await read(
        stream, mutable_buffer(header));
    if(ec == cond::eof)
        co_return;  // clean shutdown
    if(ec)
        co_return;
    // header contains exactly 16 bytes
}
----

=== `read(stream, dynamic_buffer)` -- Read Until EOF

[source,cpp]
----
auto read(ReadStream auto& stream,
          DynamicBufferParam auto&& buffers,
          std::size_t initial_amount = 2048)
    -> io_task<std::size_t>;
----

Reads from the stream into a dynamic buffer until EOF is reached. The
buffer grows with a 1.5x factor when filled. On success (EOF), `ec`
is clear and `n` is the total bytes read.

[source,cpp]
----
template<ReadStream Stream>
task<std::string> slurp(Stream& stream)
{
    std::string body;
    auto [ec, n] = co_await read(
        stream, string_dynamic_buffer(&body));
    if(ec)
        co_return {};
    co_return body;
}
----

=== `read_until(stream, dynamic_buffer, match)` -- Delimited Read

Reads from the stream into a dynamic buffer until a delimiter or match
condition is found. Used for line-oriented protocols and message
framing.

[source,cpp]
----
template<ReadStream Stream>
task<> read_line(Stream& stream)
{
    std::string line;
    auto [ec, n] = co_await read_until(
        stream, string_dynamic_buffer(&line), "\r\n");
    if(ec)
        co_return;
    // line contains data up to and including "\r\n"
}
----

== Use Cases

=== Reading Fixed-Size Records

When the protocol defines fixed-size messages, the `read` composed
algorithm fills the buffer exactly.

[source,cpp]
----
struct message_header
{
    uint32_t type;
    uint32_t length;
};

template<ReadStream Stream>
task<> process_messages(Stream& stream)
{
    for(;;)
    {
        message_header hdr;
        auto [ec, n] = co_await read(
            stream, mutable_buffer(&hdr, sizeof(hdr)));
        if(ec == cond::eof)
            co_return;  // clean shutdown
        if(ec)
            co_return;

        std::vector<char> body(hdr.length);
        auto [ec2, n2] = co_await read(
            stream, mutable_buffer(body));
        if(ec2)
            co_return;

        handle_message(hdr, body);
    }
}
----

=== Incremental Processing with `read_some`

When processing data as it arrives without waiting for a full buffer,
`read_some` is the right choice. This is common for real-time data or
when the processing can handle partial input.

[source,cpp]
----
template<ReadStream Stream>
task<> echo(Stream& stream, WriteStream auto& dest)
{
    char buf[4096];
    for(;;)
    {
        auto [ec, n] = co_await stream.read_some(
            mutable_buffer(buf));
        if(ec == cond::eof)
            co_return;
        if(ec)
            co_return;

        // Forward whatever we received immediately
        auto [wec, nw] = co_await dest.write_some(
            const_buffer(buf, n));
        if(wec)
            co_return;
    }
}
----

=== Reading into a Dynamic Buffer

When the total size is unknown, read into a dynamic buffer until EOF.
The buffer grows automatically.

[source,cpp]
----
template<ReadStream Stream>
task<std::string> read_entire_response(Stream& stream)
{
    std::string body;
    auto [ec, n] = co_await read(
        stream, string_dynamic_buffer(&body));
    if(ec)
        co_return {};
    co_return body;
}
----

=== Line-Oriented Protocol

For protocols delimited by `\r\n`, `read_until` scans the stream
for the delimiter.

[source,cpp]
----
template<ReadStream Stream>
task<> process_commands(Stream& stream)
{
    for(;;)
    {
        std::string line;
        auto [ec, n] = co_await read_until(
            stream, string_dynamic_buffer(&line), "\r\n");
        if(ec == cond::eof)
            co_return;
        if(ec)
            co_return;

        // line includes the "\r\n" delimiter
        execute_command(line);
    }
}
----

=== Relaying from ReadStream to WriteStream

When relaying data from a reader to a writer, `read_some` feeds
`write_some` directly. This is the fundamental streaming pattern.

[source,cpp]
----
template<ReadStream Src, WriteStream Dest>
task<> relay(Src& src, Dest& dest)
{
    char storage[65536];
    circular_dynamic_buffer cb(storage, sizeof(storage));

    for(;;)
    {
        // Read into free space
        auto mb = cb.prepare(cb.capacity());
        auto [rec, nr] = co_await src.read_some(mb);
        cb.commit(nr);

        if(rec && rec != cond::eof)
            co_return;

        // Drain to destination
        while(cb.size() > 0)
        {
            auto [wec, nw] = co_await dest.write_some(
                cb.data());
            if(wec)
                co_return;
            cb.consume(nw);
        }

        if(rec == cond::eof)
            co_return;
    }
}
----

Because `ReadSource` refines `ReadStream`, this relay function also
accepts `ReadSource` types. An HTTP body source or a decompressor
can be relayed to a `WriteStream` using the same function.

== Conforming Types

Examples of types that satisfy `ReadStream`:

- **TCP sockets**: `read_some` maps to a single `recv()` or
  `WSARecv()` call. Returns whatever the kernel has buffered.
- **TLS streams**: `read_some` decrypts and returns one TLS record's
  worth of application data.
- **Buffered read streams**: `read_some` returns data from an internal
  buffer, refilling from the underlying stream when empty.
- **QUIC streams**: `read_some` returns data from received QUIC frames.
- **Test mock streams**: `read_some` returns configurable data and
  error sequences for testing.

All of these types also naturally extend to `ReadSource` by adding
`read`.

== Relationship to the Write Side

[cols="1,1"]
|===
| Read Side | Write Side

| `ReadStream::read_some`
| `WriteStream::write_some`

| `read` free function (composed)
| `write_now` (composed, eager)

| `read_until` (composed, delimited)
| No write-side equivalent

| `ReadSource::read`
| `WriteSink::write`
|===

The read side does not have an eager-completion equivalent of
`write_now`. Reads depend on data arriving from the network, so the
synchronous fast path -- where the operation completes in `await_ready`
-- is less reliably useful. Writes into a buffered stream frequently
complete synchronously (just a `memcpy`), making the eager path
valuable. Reads rarely have all data pre-buffered.

== Why `read_some` Returns No Data on EOF

The `read_some` contract requires that when `ec == cond::eof`, `n`
is always 0. Data and EOF are delivered in separate calls. This is a
deliberate design decision with consequences for every consumer of
`read_some` in the library. It merits thorough explanation,
particularly because the write side offers `write_eof(buffers)` which
atomically combines the final data with the EOF signal. Why shouldn't
the read side offer the same?

=== The Write-Side Analogy

On the write side, `write_eof(buffers)` exists so the producer can
atomically deliver its final data together with the EOF signal. A
natural question follows: if the write side has atomic data-plus-EOF,
why doesn't the read side allow `read_some` to return `n > 0` with
`ec == cond::eof`? The source knows it just delivered its last
bytes -- it could piggyback EOF onto that return, saving the caller
an extra `co_await` that will only yield `(eof, 0)`.

The analogy is real but the symmetry breaks down under examination.
The two sides of the I/O boundary have fundamentally different
roles: the writer _decides_ when to signal EOF, while the reader
_discovers_ it. This asymmetry has deep implications for API design.

=== Atomicity Serves Correctness on the Write Side

`write_eof(buffers)` is not merely an optimization. It exists for
correctness. Protocol framings require the final data and the EOF
marker to be emitted together so the peer observes a complete
message:

- **HTTP chunked encoding**: the final data chunk and the terminal
  `0\r\n\r\n` must be emitted in a single operation to avoid the
  peer seeing incomplete framing.
- **Compression (deflate)**: the final `deflate()` call needs
  `Z_FINISH` to produce the stream trailer. Splitting data and
  finalization into separate calls would require an extra flush.
- **TLS close-notify**: coalescing the final application data with
  the close-notify alert avoids an extra round-trip.

On the read side, no such correctness requirement exists. Whether
the last bytes arrive with EOF or on a separate call does not change
what the reader observes. The reader receives the same bytes in the
same order regardless. Piggybacking EOF onto the last data delivery
is purely an optimization -- saving one lightweight call -- not a
correctness mechanism.

=== `write_eof` Is a Separate Function, Not a Mode

On the write side, the writer _chooses_ to call `write_eof` instead
of `write_some`. The two functions have different names and different
contracts. `write_some` never signals EOF. The caller opts into
data-plus-EOF explicitly. The call site reads `write_eof(data)` and
the intent is unambiguous.

If `read_some` could return `n > 0` with EOF, then every call to
`read_some` would be _sometimes_ a data-only operation and
_sometimes_ a data-plus-EOF operation. The caller does not choose
which mode it gets -- the stream decides at runtime. Every call site
must therefore handle both modes. This is unlike the write side,
where the caller selects the mode by choosing which function to call.

The distinction matters because it shifts the burden. On the write
side, the _caller_ decides to use the combined operation and writes
code that handles it once, at one call site. On the read side, every
_consumer_ of `read_some` across the entire codebase would have to
handle the combined case, whether they want to or not.

=== A Clean Trichotomy Simplifies Every Caller

With the current contract, every `read_some` result falls into
exactly one of three mutually exclusive cases:

- **Success**: `!ec`, `n >= 1` -- data arrived, process it.
- **EOF**: `ec == cond::eof`, `n == 0` -- stream ended, no data.
- **Error**: `ec`, `n == 0` -- failure, no data.

Data is present if and only if the operation succeeded. This
invariant -- _data implies success_ -- eliminates an entire category
of reasoning from every read loop in the codebase. The common read
loop becomes trivially simple:

[source,cpp]
----
auto [ec, n] = co_await stream.read_some(buf);
if(ec)
    break;        // EOF or error -- no data to handle
process(buf, n);  // only reached on success, n >= 1
----

The caller tests one condition and either processes data or stops.
There is no third case where data arrived but the stream also ended.

If `read_some` could return `n > 0` with EOF, the loop becomes:

[source,cpp]
----
auto [ec, n] = co_await stream.read_some(buf);
if(n > 0)
    process(buf, n);  // must handle data even on EOF
if(ec)
    break;
----

Every consumer of `read_some` in the entire codebase pays this tax:
an extra branch to handle the "data and EOF together" case. The
branch is easy to forget, and forgetting it silently drops the final
bytes of the stream -- a particularly insidious bug because it only
manifests when the source happens to deliver EOF with its last data
rather than on a separate call. A TCP socket that receives data in
one packet and FIN in a separate packet will not trigger the bug. A
memory source that knows its remaining length will. The
non-determinism makes the bug difficult to reproduce and diagnose.

The clean trichotomy eliminates this class of bugs entirely. No
caller can accidentally drop data because data never accompanies
an error or EOF result.

=== Concrete Sources Always Have a Natural Separation

Every concrete `ReadStream` implementation naturally separates its
last data delivery from its EOF signal:

- **TCP sockets**: the kernel delivers buffered bytes on one
  `recv()` call and returns 0 on the next. The separation is
  inherent in the POSIX API.
- **TLS streams**: the TLS record layer delivers decrypted
  application data. The close-notify alert arrives as a separate
  record.
- **HTTP content-length body**: the source delivers bytes up to
  the content-length limit. Once the limit is reached, the next
  `read_some` returns EOF. There is always a final call that
  delivers the limit-reaching bytes and a subsequent call that
  returns EOF.
- **HTTP chunked body**: the unchunker delivers decoded data from
  chunks. The terminal `0\r\n\r\n` is parsed on a separate pass
  that returns EOF.
- **Compression (inflate)**: the decompressor delivers output bytes.
  When `Z_STREAM_END` is detected, the next read returns EOF.
- **Memory source**: returns `min(requested, remaining)` bytes. When
  `remaining` reaches 0, the next call returns EOF.

No concrete source type is forced into an unnatural pattern by the
`n == 0` on EOF rule. Every source already has a natural boundary
between its last data and its EOF indication.

=== The Saved Call Is Cheap

The extra `read_some` that returns `(eof, 0)` is a lightweight
operation. The source checks its internal state, finds the stream
exhausted, and returns immediately. There is no system call, no
network round-trip, no meaningful I/O. For a memory source, it is
a comparison of an offset against a length. For a TCP socket, the
kernel already knows the connection is closed and returns 0
immediately. For a decompressor, the inflater's internal state flag
is already set.

One coroutine suspend and resume at the tail end of an entire stream
transfer is negligible. If the stream transferred megabytes of data
across hundreds of `read_some` calls, one final `(eof, 0)` call adds
immeasurable overhead. The cost is zero system calls, zero network
round-trips, and a single coroutine resume that executes a handful of
instructions.

=== Composed Operations Handle Partial Data on EOF

The `read` composed algorithm (and `ReadSource::read`) _does_ allow
`n > 0` on EOF, because it is a composed loop that accumulates data
across multiple internal `read_some` calls. When the underlying
stream signals EOF mid-accumulation, discarding the bytes already
gathered would be wrong. The caller needs `n` to know how much valid
data landed in the buffer.

The design separates concerns cleanly: the single-shot primitive
(`read_some`) delivers unambiguous results with a clean trichotomy.
Composed operations that accumulate state (`read`) report what they
accumulated, including partial results on EOF. This layering means
callers who need partial-on-EOF semantics get them through the
composed layer, while the primitive layer remains simple.

=== POSIX Precedent

The POSIX `read()` system call returns 0 to signal EOF, with no
bytes transferred. The kernel does not return "here are your last
5 bytes, and also EOF." It returns the available bytes on one call,
then returns 0 on the next. This convention is understood by
millions of programs and decades of systems code. `read_some`
follows the same model.

Every C and C++ programmer who has written a read loop expects
this behavior. Deviating from it would surprise the majority of
the target audience and introduce a novel error pattern into code
that developers have been writing correctly for decades.

== Why No `read_eof`

On the write side, `WriteSink` has `write_eof` because the writer
signals end-of-data. On the read side, the source signals EOF by
returning `cond::eof` -- the consumer detects it, it does not signal
it. The asymmetry is inherent: the producer signals EOF, the consumer
observes it.

A hypothetical `read_eof` would make no sense. The reader does not
tell the stream to end. The reader discovers that the stream has
ended. EOF flows from producer to consumer, not the other way around.

== Summary

`ReadStream` provides `read_some` as the single partial-read
primitive. This is deliberately minimal:

- Algorithms that need to fill a buffer completely use the `read`
  composed algorithm.
- Algorithms that need delimited reads use `read_until`.
- Algorithms that need to process data as it arrives use `read_some`
  directly.
- `ReadSource` refines `ReadStream` by adding `read` for
  complete-read semantics.

The choice between `read_some` and `read` is a control-versus-convenience
trade-off. `read_some` gives the caller maximum control over how much
data is consumed per iteration. `read` gives the caller the guarantee
that the buffer is completely filled.
