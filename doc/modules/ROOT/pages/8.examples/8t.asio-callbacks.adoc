= Using a Capy Stream from Asio
:page-mode: how-to

include::partial$diagram-style.adoc[]

Drive a Capy cpp:any_stream[] with Asio completion tokens, here plain callbacks.

[NOTE]
====
`example/CMakeLists.txt` adds this example only when a `Boost::asio` target is available.
`b2` builds it through `example/Jamfile`, and CI does not build it.
The full source is in `example/asio/`: `asio_callbacks.cpp`, and the adapter in `api/uni_stream.hpp`.
Both use `api/capy_streams.hpp`, which declares `asio_context` and `make_stream_pair`.
====

== What This Example Shows

* An adapter, `uni_stream`, that gives a cpp:any_stream[] the Asio universal asynchronous model with `net::async_initiate`
* Each operation starting a Capy task with cpp:run_async[], on an executor that posts through Asio
* `net::async_write` and `net::async_read` composed over the adapter
* Two callback chains that share one Asio `io_context`

== Walkthrough

=== The Initiation

`uni_stream` holds a cpp:any_stream[] and a pointer to the `asio_context`.
Its `async_read_some` passes three things to `net::async_initiate`: an `initiate_async_read_some` object, the completion token, and the buffers.
The completion token decides what `async_read_some` returns.
With a plain callback, it returns nothing.

Asio then calls `initiate_async_read_some` with the completion handler and the buffers.
The initiation looks up the executor associated with the completion handler.
The default is the executor of the `io_context`.

The initiation wraps that executor in `asio_executor_wrapper`, a Capy executor that posts every continuation through Asio.
Then it starts a task with cpp:run_async[] on the wrapper.
The task converts the buffers with `capy::from_asio`, awaits `read_some` on the cpp:any_stream[], and calls the completion handler with the error code and the byte count.

The wrapper posts even when Capy asks it to dispatch.
So the completion handler never runs inside the call to `async_read_some`, and it runs on the associated executor, as Asio requires.
`async_write_some` and `initiate_async_write_some` follow the same pattern for writes.

=== A Callback Chain

`do_write` keeps its state in a `std::shared_ptr`, so every copy of the function object shares it.
Each call writes one chunk of up to 128 bytes with `net::async_write`.
That composed operation calls `async_write_some` on the adapter until the whole chunk is written.

The completion handler of each write adds the bytes written, prints the total, and calls a copy of `do_write` again.
The chain ends when it has written 1024 bytes.
`do_read` is the same chain for `net::async_read`.

`main` makes a connected pair of adapters with `make_uni_pair`, starts both chains, and calls `ctx.run()`.
The call returns when both chains end and no work remains.
