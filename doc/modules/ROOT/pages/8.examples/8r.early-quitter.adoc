= Writing Your Own Task Type (Early Quitter)
:page-mode: how-to

include::partial$diagram-style.adoc[]

Build a task type whose coroutines end at their current `co_await` when a stop is requested.
The bodies of these coroutines contain no cancellation checks.
The type uses only the public cpp:ContextAwaitable[] protocol from xref:4.coroutines/4e.context-awaitable.adoc[The ContextAwaitable Protocol].

[NOTE]
.Example code, not library API
====
`early::quitter` lives in `example/early-quitter/quitter.hpp`.
It is not part of Capy: it has no reference page and no stability guarantee.
Copy it and adapt it.
Capy contained a `quitter` type until https://github.com/cppalliance/capy/pull/481[pull request #481] moved it into this example.
https://github.com/cppalliance/capy/discussions/431[Discussion #431] records that decision.
====

== What This Example Shows

* A second task type that satisfies cpp:ContextAwaitable[] and cpp:ContextRunnable[], as xref:4.coroutines/4e.context-awaitable.adoc#_contextrunnable_concept[ContextRunnable Concept] defines it
* A stop policy that ends the body instead of resuming it
* Shutting down on `Ctrl+C`, with RAII cleanup across a chain of quitters
* The constraints that a task type built outside the library accepts

[NOTE]
.Why this example exists
====
An application that shuts down wants every task in flight to end cleanly.
With cpp:task[], each `co_await` that can see the stop needs a check such as `if(ec) co_return;` after it.
The sender model avoids those checks with `set_stopped`, because the stopped coroutine never resumes.
A quitter gives a Capy coroutine the same behavior.
====

== Choosing Between `task` and a Quitter

Capy's only task type is cpp:task[task<T>], and Capy has no separate `io_task`.
Use cpp:task[] by default.

A quitter fits when a stop always means "drop the work and release its resources."
Application shutdown is the usual case, especially across call chains with many suspension points.
The header comment of `shutdown.cpp` shows the alternative: with cpp:task[], each wait needs `if(ec) co_return;` after it.

[cols="1,2,2"]
|===
| | `task` | `early::quitter`

| Status
| A library type with a reference page
| Example code in namespace `early`

| On a stop
| The body resumes, and stop-aware operations report `canceled`
| The body is not resumed: when the pending operation completes, the run of quitters ends

| Checks in the body
| Wherever the body must react to a stop
| None

| What the first awaiter outside the quitters receives
| The result of the task
| `canceled`, as the result of the quitter

| Result type at that boundary
| Any `T`
| `results<...>` or `std::error_code`, checked at compile time

| When the locals of a stopped coroutine are destroyed
| Before the completion handler runs
| After the completion handler returns, under cpp:run_async[]

| A stop requested before the start
| The body runs and sees the stop through its checks and its operations
| The body runs to its first `co_await`, which stops without starting that operation

| Cost of each `co_await`
| No stop check of its own
| Two stop checks; a `co_await` that suspends also resumes a gate frame
|===

xref:4.coroutines/4f.cancellation.adoc[Stop Tokens and Cancellation] describes how a cpp:task[] observes a stop.

[NOTE]
.Why a separate type
====
The task type is a policy point.
A program that wants explicit error handling uses cpp:task[].
A program that wants a stop to end the work without checks uses a quitter.
The cpp:ContextAwaitable[] protocol does not require one task type, so both work with the same launchers and combinators.
xref:9.design/9m.WhyNotAsio.adoc#_coroutine_execution_model[Coroutine Execution Model] lists user-defined task types among the features of the protocol.
====

== Walkthrough

=== A Call Chain with No Cancellation Checks

In `main.cpp`, `fetch` and `store` each await the waker twice.
Each wait stands in for one I/O operation.
`process_item` awaits `fetch`, then `store`, and `worker` calls `process_item` in an endless loop.

None of these functions looks at a stop token.
Each `resource_guard` stands in for a connection, a file, or a buffer, and logs its release.
With cpp:task[], every wait would need the check from xref:8.examples/8f.timeout-cancellation.adoc#_checking_for_cancellation[Checking for Cancellation].
xref:4.coroutines/4f.cancellation.adoc#_checking_the_token[Checking the Token] describes that check.

Only `worker` returns `early::quitter<std::error_code>`, because it is the top of the run, and its result must carry the stop.
The other three can use a result type that need not carry the stop, because only another quitter awaits them.

=== Starting the Workers

The cpp:run_async[] loop at the end of `main` starts one `worker` on each strand.
The completion handler takes the result of the worker, a `std::error_code`.
After a stop, that result is `canceled`.

Each worker gets its own strand and its own cpp:async_waker[].
A waker needs an executor that never runs its continuations concurrently, as xref:4.coroutines/4l.synchronization.adoc#threading-model[The Threading Model] explains.

=== Shutting Down from a Signal

The signal handler `on_signal` only sets `g_signaled`, a lock-free atomic flag.
It cannot call `request_stop()` on `g_stop`, because that call runs the stop callbacks, which post and allocate.
Neither is safe inside a signal handler.

The ticker thread in `main` checks the flag every `20 ms`.
Once the flag is set, the ticker calls `g_stop.request_stop()`.
On each tick, the ticker also wakes every waker, standing in for I/O completions.

Capy has no signal facility.
Signal handling needs a platform reactor, so for now it belongs in Corosio, as xref:9.design/9b.Separation.adoc#_what_lives_where[What Lives Where] explains.
https://github.com/cppalliance/capy/discussions/432[Discussion #432] about signals in Capy is still open.

=== Operations Resume a Gate

The promise of a quitter wraps each awaited operation in a `transform_awaiter`, in `quitter.hpp`.
Its `await_suspend` hands the operation the handle of a gate instead of the handle of the body.
A child quitter receives the same gate handle.

The gate is a small coroutine frame of type `gate`.
`make_gate` creates it the first time an awaited operation is not ready, and `~promise_base` destroys it.
The gate loops on `decide_awaiter`, which calls `promise_base::decide` each time an operation resumes the gate.
`decide` resumes the body, unless a stop is pending and the result ends the quitter.

The quitter never abandons an operation in flight.
It acts when that operation completes.
A stop-aware operation, such as the `wait()` of an cpp:async_waker[], completes at once with `canceled`, because its stop callback posts the resumption.

=== A Stop Ends the Run from the Top

When `decide` ends the quitter, it calls `promise_base::stop`.
That function walks the `parent_` pointers to the topmost quitter of the run, and marks each quitter on the way as stopped.
It stores `canceled` as the result of the top quitter, then returns the continuation of that quitter.
No body in the run resumes.

=== Results That Race a Stop

`transform_awaiter::await_ready` and `transform_awaiter::await_suspend` decide what a stop does to an operation.
There are two cases.

*A stop is already pending when the `co_await` begins.*
`await_ready` checks for the stop before it asks the operation anything, and reports that the operation is not ready.
`await_suspend` then calls `stop()`.
The operation is never started, so nothing, such as a lock or a buffer, is acquired only to be dropped.
Nothing is delivered, and the run stops.

*A stop arrives while the operation completes.*
The stop can arrive inside the readiness check of the operation.
It can also arrive after the operation completes, but before the gate runs.
In both cases, `stops_on_completion` takes the result early:

* A `canceled` result ends the quitter.
* Any other `results<...>` or `std::error_code` value is delivered to the body.
  The stop takes effect at the next `co_await`.
* A result that cannot carry the stop, such as `void`, a reference, or any other type, is dropped, and the quitter ends.
  The operation still hands the result over, so anything it owns is destroyed.
* An exception from the operation reaches the body.
  The stop takes effect at the next `co_await`.

The constant `holds` in `transform_awaiter` decides which results the quitter can keep.
It uses the trait `carries_stop`, described in the next section.

=== The Boundary Rule

A stop becomes a value at the first awaiter that is not a quitter.
That awaiter can be a task, cpp:run[], cpp:run_async[], or cpp:when_all[], and it receives `canceled` as the result of the quitter.
So the result type at that boundary must be able to hold `canceled`.

The trait `carries_stop` accepts `std::error_code` and any `std::tuple<std::error_code, Ts...>`, which includes cpp:results[].
The `static_assert` in `set_continuation` checks a quitter that a launcher starts.
A second `static_assert`, in `quitter::await_suspend`, checks a quitter that a task or a combinator awaits.
A quitter with any other result type at the boundary is a compile error.

=== Cleanup Runs After the Completion Handler

A stopped quitter keeps its locals until its owner destroys the frame.
Under cpp:run_async[], the completion handler runs first, and then the frame is destroyed.
So a completion handler that counts down a latch can wake `main` before the resource guards run.

`shutdown.cpp` handles this in `main`.
After `done.wait()`, it joins the ticker, then calls `pool.join()`, and only then reads the counters that the guards update.

`main.cpp` prints its final message without calling `pool.join()`.
Pool threads can still be destroying frames, so `released` lines can follow that message.
`main.cpp` needs no `pool.join()` for this, because only the order of its output lines depends on it.
It reads no state that the guards update.

The strands and the wakers are destroyed before the pool, and that is safe here for two reasons.
Each cpp:run_async[] call keeps its own copy of its strand, and the copies share one reference-counted state.
A waiter that a wake or a stop already claimed never touches its waker again.
Real code should still copy the order in `shutdown.cpp`.

[WARNING]
====
* Wait for the work of the executor, for example with `thread_pool::join`, before you read state that the destructors of a quitter touch.
* A quitter that another coroutine or a combinator awaits may be destroyed unfinished in two cases only.
  Either its run stopped, or an abandoned chain unwinds it.
  In any other case, `destroy_frame` calls `std::terminate`.
====

== What the Self-Checks Cover

`checks.cpp` runs 13 checks on a single-threaded queue, except the last one, which uses a thread pool:

* `value_without_stop`: without a stop, the value of a quitter reaches the completion handler unchanged.
* `deep_stop_while_suspended`: a stop ends three nested quitters at once, no body resumes, and all three guards run.
* `stop_before_start`: with the stop requested before the start, the body runs up to its first `co_await` and ends there.
* `ready_success_then_stop_delivers`: a stop arrives while a ready operation completes, the successful result is delivered, and the next `co_await` stops.
* `ready_canceled_then_stop_stops`: the same race with a `canceled` result ends the quitter at once.
* `stop_pending_leaves_operation_untouched`: with a stop pending at a `co_await`, the operation is never started.
* `early_exception_reaches_body`: an exception from a result taken early reaches the body.
* `stop_after_wake_before_gate`: a stop arrives after a wake posts the gate, but before the gate runs.
  The wake is delivered, and the next `co_await` stops.
* `task_between_quitters`: a task between two quitters receives `canceled` as a value, and the outer quitter then ends.
* `exception_propagates`: an exception from the body of a child quitter reaches the parent quitter.
* `teardown_through_closed_executor`: the waker posts the gate to a closed executor, which abandons it.
  The chain unwinds, and no completion handler runs.
* `when_all_branches_stop`: two quitters in the branches of cpp:when_all[] both stop, and the task that awaits cpp:when_all[] resumes.
* `stop_races_wake`: a wake and a stop from two threads race 2000 times against a quitter on a thread pool.
  Each run completes exactly once, and its frame always unwinds.

Run them with `ctest --test-dir build -R early_quitter`.

== Known Limitations

* A stop requested before the start still lets the body run to its first `co_await`.
* A result that cannot carry the stop is dropped when a stop arrives as the operation completes.
  That includes a reference result and a `const`-qualified result, because `carries_stop` matches neither.
* A stopped `results<Ts...>` needs default-constructible `Ts`.
* cpp:task[] works around a symmetric-transfer limit of MSVC, and the quitter does not.
* The checks do not cover cpp:run[] onto another executor, cpp:when_any[], or a handoff through a strand or a mutex.
