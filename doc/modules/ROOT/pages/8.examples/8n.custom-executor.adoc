= Custom Executor
:page-mode: how-to

Implementing the xref:glossary.adoc#executor[Executor] concept with a single-threaded run loop.

== What This Example Shows

* Satisfying the cpp:Executor[] concept
* Deriving from cpp:execution_context[], and implementing cpp:Executor::dispatch[dispatch] and cpp:Executor::post[post]
* Running Capy coroutines on a custom scheduling system

== Walkthrough

=== Inheriting execution_context

[source,cpp]
----
include::example$custom-executor/custom_executor.cpp[tag=inherit]
----

The destructor tears the loop down in five steps:

. Reset `owner_`, so `dispatch` no longer resumes anything inline.
. Call `shutdown()`, so each service gives up its work.
. Drain the queue, giving up each queued cpp:continuation[] with cpp:abandon[]. The drain also takes work posted while it runs.
. Call `destroy()`. No service may be created after this call.
. Drain once more, for any work a service destructor posts anyway.

The queue holds copies of each continuation, and each copy carries the owner that cpp:abandon[] needs.
xref:4.coroutines/4j.lifetimes.adoc#_shutdown_ordering[Shutdown Ordering] describes what abandoning a chain does.

=== The Executor Concept

The nested `executor_type` must provide:

* cpp:Executor::context[context()] -- returns a reference to the owning cpp:execution_context[]
* cpp:Executor::on_work_started[on_work_started()] / cpp:Executor::on_work_finished[on_work_finished()] -- work-tracking hooks
* `dispatch(c)` -- resume immediately if already on this context, otherwise enqueue. Takes a cpp:continuation[]`&` and returns `std::coroutine_handle<>`.
* `post(c)` -- always enqueue for later execution. Takes a `continuation&`.
* cpp:Executor::operator==[+operator==+] -- compare two executors for identity

----

=== Dispatch vs Post

[source,cpp]
----
include::example$custom-executor/custom_executor.cpp[tag=dispatch,indent=0]
----

`dispatch` takes a `continuation&` and checks whether the caller is already running on the loop's thread. If so, it returns `c.h` directly for inline resumption via xref:glossary.adoc#symmetric-transfer[symmetric transfer]. Otherwise it enqueues a copy of `c` and returns `noop_coroutine` so the caller continues without blocking.

`post` always enqueues, even if already on the right thread.

=== Driving the Loop

[source,cpp]
----
include::example$custom-executor/custom_executor.cpp[tag=drive,indent=0]
----

cpp:run_async[] dispatches the initial coroutine. The loop is not running yet, so `dispatch` enqueues it. `loop.run()` drains the queue, resuming coroutines one by one until all work completes.

`run()` uses `capy::safe_resume(h)` instead of `h.resume()`. This saves and restores the thread-local xref:glossary.adoc#frame-allocator[frame allocator] around each resumption, preventing coroutines from spoiling each other's allocator. All custom executor event loops must use cpp:safe_resume[] -- see xref:4.coroutines/4h.allocators.adoc#_tls_preservation[TLS Preservation] for details.

== Exercises

1. Add a `stop()` method that causes `run()` to exit early, even with work remaining
2. Make the run loop thread-safe so work can be posted from other threads
3. Integrate the run loop with a platform event system (e.g., `epoll` or `kqueue`). For the GUI-framework case, xref:8.examples/8q.gui-integration.adoc[GUI Integration] works the example through, including where a coroutine resumes after awaiting work that finished on another thread
