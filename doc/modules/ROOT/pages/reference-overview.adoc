= Reference
:page-mode: reference

This page groups the public Capy API by purpose.
Each name links to its generated reference page.
The xref:reference:boost/capy.adoc[index by kind] lists these names, plus namespaces and operators, by entity kind.

All names are in namespace `boost::capy`.
Testing tools are in cpp:test[], and the coroutine accessors are in cpp:this_coro[].
Operators are listed on the page of their type.

[#tasks-and-promise-types]
== Tasks and Promise Types

cpp:task[] is Capy's only task type, the return type for coroutines that perform I/O.
A task's body does not run until the task is awaited or started.
cpp:run_async[] and cpp:run[] start any type that satisfies cpp:ContextRunnable[].
Authors of other task types build their promise type from the mixins in this section.
See xref:4.coroutines/4b.tasks.adoc[The task Type] and xref:4.coroutines/4e.context-awaitable.adoc[The ContextAwaitable Protocol].

[#starting-and-composing-tasks]
== Starting and Composing Tasks

cpp:run_async[] starts a task from code that is not a coroutine.
Inside a coroutine, `co_await` cpp:run[] to execute a task on a chosen executor, or with its own stop token or frame allocator.
cpp:when_all[] and cpp:when_any[] concurrently run several awaitables that return cpp:results[].
cpp:when_all[] waits for all of them, and cpp:when_any[] picks the first one that succeeds.
See xref:4.coroutines/4c.launching.adoc[Starting Coroutines] and xref:4.coroutines/4g.composition.adoc[Concurrent Composition].

[#executors-and-execution-contexts]
== Executors and Execution Contexts

An executor dispatches or posts continuations to its execution context.
An execution context, such as cpp:thread_pool[], provides executors bound to its own resources.
cpp:strand[] serializes the coroutines dispatched through it.
Authors of custom executors queue cpp:continuation[] objects and resume their handles with cpp:safe_resume[].
See xref:4.coroutines/4d.executors.adoc[Executors and Execution Contexts] and xref:8.examples/8n.custom-executor.adoc[Custom Executor].

[#coroutine-environment]
== Coroutine Environment

Each coroutine in a chain receives an cpp:await_context[] that carries its executor, stop token, and frame allocator.
Inside a task, `co_await` an object from cpp:this_coro[] to read one of them, or cpp:this_coro::environment[] to read all three.
For example, `co_await` cpp:this_coro::stop_token[] fetches the running coroutine's stop token.
See xref:4.coroutines/4e.context-awaitable.adoc[The ContextAwaitable Protocol] and xref:4.coroutines/4f.cancellation.adoc[Stop Tokens and Cancellation].

[#synchronization]
== Synchronization

These primitives suspend a task instead of blocking its thread.
cpp:async_mutex[] grants exclusive access, cpp:async_event[] resumes every waiter, and cpp:async_waker[] hands one wakeup to one waiter.
To serialize all work without a lock, use the cpp:strand[] from <<executors-and-execution-contexts>>.
See xref:8.examples/8l.async-mutex.adoc[Async Mutex], xref:8.examples/8b.producer-consumer.adoc[Producer-Consumer], and xref:8.examples/8f.timeout-cancellation.adoc[Timeout with Cancellation].

[#frame-allocators]
== Frame Allocators

A task's `operator new` takes its frame from the thread's current frame allocator.
cpp:run_async[] sets that allocator before it creates the task.
Without an explicit allocator, it uses the execution context's frame allocator, which is the recycling allocator unless replaced.
Code that resumes a coroutine handle directly calls cpp:safe_resume[], which restores the thread's frame allocator after the coroutine yields control.
Promise types get allocator support from cpp:frame_alloc_mixin[], listed under <<tasks-and-promise-types>>.
See xref:4.coroutines/4h.allocators.adoc[Frame Allocators].

[#chain-ownership-and-abandonment]
== Chain Ownership and Abandonment

Each xref:glossary.adoc#segment[segment] of a coroutine chain has a cpp:chain_owner[].
A holder that can never resume a suspended coroutine gives it up with cpp:abandon[].
Execution contexts do this when they shut down, and so do strands when their execution context shuts down.
Abandonment also travels up a chain: when a coroutine started by cpp:when_all[], cpp:when_any[], cpp:run[] or cpp:test::run_blocking[] is abandoned, its caller is abandoned too.
A destroyed cpp:async_mutex[] or other primitive instead resumes its waiters with a canceled error.
See xref:4.coroutines/4j.lifetimes.adoc[Lifetime and Ownership].

[#buffers]
== Buffers

A buffer refers to a contiguous region of memory.
A buffer sequence is one buffer or a range of them.
cpp:make_buffer[] makes a buffer from a region of memory, a string view, or a contiguous range.
The other functions measure a buffer sequence, copy it, return its first buffer, or iterate over its buffers or bytes.
Each archetype satisfies its sequence concept but has no default constructor.
See xref:5.buffers/5.intro.adoc[Buffer Sequences].

[#streams]
== Streams

A stream reads into or writes from buffer sequences.
cpp:read[] fills the whole buffer sequence, and cpp:write[] writes all of it, unless an error stops them first.
Each function in this section is awaited with `co_await`.
The type-erased wrappers accept any stream that satisfies the matching concept and hide its type.
See xref:6.streams/6.intro.adoc[Streams].

[#testing]
== Testing

The tools in cpp:test[] drive tasks and streams without a real I/O backend.
cpp:test::run_blocking[] starts a task and waits on the calling thread until it completes.
cpp:test::fuse[] injects a failure at a different point on each pass.
cpp:set_current_thread_name[] is in `boost::capy`, but its header is `<boost/capy/test/thread_name.hpp>`.
See xref:7.testing/7.intro.adoc[Testing].
