= Lambda Coroutine Captures
:page-mode: how-to

Lambda captures are a common source of undefined behavior in coroutine code.

== The Problem

The lambda is defined and called in one expression -- the `()` after the closing brace -- so `started` holds the task, not the lambda. That shape is an _immediately invoked function expression_, or IIFE; it matters again below.

[source,cpp]
----
include::example$snippets/4i_lambda_captures.cpp[tag=dangling_capture]
----

**This code has undefined behavior.** It may crash, corrupt memory, or appear to work until it doesn't.

== Why It Fails

In {cpp}20, lambda coroutine captures are stored in the lambda closure object, *not* in the xref:glossary.adoc#coroutine-frame[coroutine frame]. Here is what happens:

1. The lambda closure is created, capturing `sock` by reference
2. The lambda's `operator()()` is called
3. A coroutine frame is allocated (typically on the heap; HALO may elide this)
4. The coroutine suspends at `initial_suspend`
5. `operator()()` returns the task
6. **The lambda closure is destroyed**, because it was a temporary
7. Later, the coroutine resumes
8. The coroutine accesses `sock` through the destroyed closure
9. **Undefined behavior**

The coroutine frame does not contain a copy of the captured `sock`. It contains a reference to the lambda's capture storage, which no longer exists.

[NOTE]
====
{cpp} copies a coroutine's parameters into the coroutine frame, but the closure object is not one of them. The coroutine is the closure's `operator()`, and its body reaches each capture through the closure's `this`. The frame stores only that pointer, so the captures die with the closure.
====

== The Safe Pattern: IIFE With Parameters

The solution is to pass values as **function parameters** instead of **lambda captures**. Function parameters are copied to the coroutine frame.

== When Are Captures Safe?

Captures are only safe when the lambda object **outlives the coroutine**:

[source,cpp]
----
include::example$snippets/4i_lambda_captures.cpp[tag=stored_lambda_safe,indent=0]
----

This pattern is rare. Most async code immediately invokes the lambda and discards it, making captures unsafe.

== Rules of Thumb

1. **Default to IIFE with parameters** for lambda coroutines
2. **Never capture by reference** (`[&]`) in a lambda coroutine unless the lambda outlives the coroutine
3. **Capturing by value** (`[=]`, `[x]`) is equally broken: the copy lives in the lambda, not the coroutine frame
4. **Capturing `this`** is particularly dangerous and common: the body reads like a member function, but every member access goes through the closure
5. **When in doubt, use parameters**

== Alternative: Named Coroutine Functions

If the IIFE syntax feels awkward, use a named function instead:

[source,cpp]
----
include::example$snippets/4i_lambda_captures.cpp[tag=named_member_coroutine]
----

Member function coroutines work correctly because `this` is an implicit parameter, not a capture. The compiler copies the pointer to the coroutine frame, so the object itself must outlive the coroutine.

== Quick Reference

[cols="2,1,2"]
|===
| Pattern | Safety | Notes

| `[](auto x) -> capy::task<> { use(x); }(val)`
| SAFE
| Parameter `x` in coroutine frame

| Member function coroutine
| SAFE*
| `this` is an implicit parameter. The object must outlive the coroutine

| `[](auto& x) -> capy::task<> { use(x); }(val)`
| SAFE*
| Reference parameter; `val` must outlive coroutine

| `[x]() -> capy::task<> { use(x); }()`
| UNSAFE
| Capture `x` destroyed with lambda

| `[&x]() -> capy::task<> { use(x); }()`
| UNSAFE
| Accessed through the destroyed closure
|===
