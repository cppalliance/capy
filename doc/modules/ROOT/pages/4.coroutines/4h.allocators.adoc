= Frame Allocators
:page-mode: explanation

Every task you start allocates a xref:glossary.adoc#coroutine-frame[coroutine frame], and a server that starts many short tasks pays that cost on each one. Capy routes these allocations through a xref:glossary.adoc#frame-allocator[frame allocator]. The execution context's default, cpp:recycling_memory_resource[], recycles freed frames, so steady-state work rarely reaches the heap. cpp:thread_pool[] uses `std::allocator<void>` instead unless you change it. This page explains the choices you have, and then the mechanism that carries the allocator to every frame in a chain.

=== Default Allocator

When no allocator is specified, cpp:run_async[] uses the xref:glossary.adoc#execution-context[execution context]'s frame allocator. An execution context starts with cpp:recycling_memory_resource[], which is optimized for xref:glossary.adoc#coroutine-frame[coroutine frame] sizes. A context may replace it: cpp:thread_pool[] uses `std::allocator<void>`. Call `set_frame_allocator` on the context to choose another.

== Custom Allocator Requirements

Custom allocators must meet the usual {cpp} allocator requirements, or be a `std::pmr::memory_resource*`. The library does not expose a separate public concept for them; a value-type allocator works as a frame allocator when it provides, illustratively:

.Illustrative requirements - not a named concept
[source,cpp,role=pseudocode]
----
typename A::value_type;
a.allocate(n)        // -> A::value_type*
a.deallocate(p, n);
----

The allocator must also be copy constructible. When passed to cpp:run_async[], it must be nothrow move constructible as well. Capy checks both at compile time.

Frames allocated through a value-type allocator are aligned to the default new alignment (`__STDCPP_DEFAULT_NEW_ALIGNMENT__`, 16 bytes on common platforms). Capy rebinds the allocator to another `value_type` and requests whole multiples of that alignment, so each request's size is rounded up. Frames that need more alignment are not supported.

== Recycling Memory Resource

Capy provides cpp:recycling_memory_resource[], a memory resource optimized for coroutine frames:

* Maintains freelists by size class
* Reuses recently freed blocks (cache-friendly)
* Sends requests over 2048 bytes, and misses in both its pools, to `::operator new`

An execution context uses this resource by default. cpp:thread_pool[] replaces it with `std::allocator<void>`.

NOTE: cpp:recycling_memory_resource[] honors only the default new alignment (`__STDCPP_DEFAULT_NEW_ALIGNMENT__`, 16 bytes on common platforms). The alignment argument passed to cpp:recycling_memory_resource::do_allocate[do_allocate]/cpp:recycling_memory_resource::do_deallocate[do_deallocate] is ignored, so over-aligned requests are not satisfied. This is sufficient for coroutine frames but means the resource is not a drop-in replacement where over-aligned allocations are required.

== HALO Optimization

*Heap Allocation eLision Optimization* (HALO) allows the compiler to allocate coroutine frames on the stack instead of the heap when:

* The coroutine's lifetime is provably contained in the caller's
* The frame size is known at compile time
* Optimization is enabled

=== GCC vs Clang Frame Sizes

NOTE: This section draws on https://chuanqixu9.github.io/c++/2026/03/27/C++20-Coroutines-from-compiler-and-library-authors-perspective.en.html[C++20 Coroutines from compiler and library authors' perspective] by Chuanqi Xu.

GCC and Clang use fundamentally different strategies for coroutine frame layout:

* **Clang** performs frame layout after middle-end optimizations. Dead variables, unused temporaries, and constant-folded intermediates are eliminated before the frame is sized.
* **GCC** performs frame layout in the frontend, before optimizations. Every local variable whose scope spans a suspend point ends up in the frame, even if optimizations would later prove it dead.

How large the gap gets depends on how much the optimizer can discard. Without optimization the two are comparable, as the table above shows. With optimization enabled, Clang's frames can be smaller by an order of magnitude or more. The cited article reports a coroutine whose frame was 24 bytes on Clang against 16,032 bytes on GCC.

For production coroutine workloads, Clang currently produces substantially better code. On GCC, do not rely on scoping; keep large buffers outside the frame, and consider a custom `memory_resource` with larger block sizes. Frames above 2048 bytes bypass the default recycling memory resource's pooling.

=== Profile Before Optimizing

Coroutine frame allocation is rarely the bottleneck. Profile your application before investing in custom allocators.


== How Frame Allocation Works

The sections below are the mechanism behind everything above. You do not need them to use a custom allocator, but you do need them to write an executor or a promise type.

[#timing-constraint]
=== The Timing Constraint

Coroutine frame allocation has a unique constraint: memory must be allocated *before* the coroutine body begins executing. The standard {cpp} mechanism, the promise type's `operator new`, is called before the promise is constructed.

How can a coroutine use a custom allocator when the allocator might be passed as a parameter, which is stored *in* the frame?

[#two-call-rationale]
=== Thread-Local Propagation

Capy solves this with a per-thread frame allocator pointer, kept in thread-local storage (TLS):

1. Before the task argument is evaluated, cpp:run_async[] installs its allocator in TLS. cpp:run[] does the same when given an allocator.
2. The task's `operator new` reads that allocator. It stores the allocator at the tail of the frame, so the frame is freed through the same resource.
3. The starting function also gives the task an xref:glossary.adoc#environment[environment] that carries the allocator. By the end of the expression that started the task, it restores the TLS value it found.

This is why cpp:run_async[] uses two-call syntax:

[source,cpp]
----
include::example$snippets/4h_allocators.cpp[tag=two_call,indent=0]
----

Three patterns split those two calls apart, and two of them do it without any
diagnostic. xref:4.coroutines/4c.launching.adoc[Starting Coroutines] lists all
three.

=== Reinstalling on Resume

A task never relies on TLS still holding its allocator. The task is lazy, so its body may start later or on another thread. When the body starts, the task reinstalls TLS from its environment. It does so again each time it resumes from a `co_await`.

A child task created in the body therefore allocates from the parent's allocator, whichever thread runs the body and whenever it runs. Awaiting the child hands it the parent's environment, so the child does the same for its own children.

=== TLS Preservation

Between a coroutine's `await_resume` (which sets TLS to the correct allocator) and the next child coroutine invocation (whose `operator new` reads TLS), arbitrary user code runs. That code can call `.resume()` directly, pump a completion queue, or run nested dispatch. If it resumes a coroutine from a different chain on the same thread, the other coroutine's `await_resume` overwrites TLS with its own allocator. The original coroutine's next child would then allocate from the wrong resource.

To prevent this, any code that calls `.resume()` on a xref:glossary.adoc#coroutine-handle[coroutine handle] must use cpp:safe_resume[] from `<boost/capy/ex/frame_allocator.hpp>`:

[source,cpp]
----
include::example$snippets/4h_allocators.cpp[tag=safe_resume,indent=0]
----

cpp:safe_resume[] saves the current thread-local allocator, calls `h.resume()`, then restores the saved value. This makes TLS behave like a stack: nested resumes cannot spoil the outer value. All of Capy's built-in executors (cpp:thread_pool[], xref:glossary.adoc#strand[strands], cpp:test::blocking_context[blocking_context]) use `safe_resume` internally. Custom executor event loops must do the same -- see xref:8.examples/8n.custom-executor.adoc[Custom Executor] for an example.

[NOTE]
====
cpp:safe_resume[]'s implementation:

[source,cpp]
----

----

The cost is two TLS accesses (one read, one write) per `.resume()` call, negligible compared to the cost of resuming a coroutine.

Two `.resume()` call sites intentionally do _not_ use cpp:safe_resume[]:

* **`symmetric_transfer`** (MSVC workaround). The calling coroutine is about to suspend unconditionally. When it later resumes, `await_resume` restores TLS from the promise's stored environment. Save/restore would add overhead with no benefit.
* **`run_async_wrapper::operator()`**. TLS is already saved in the wrapper's constructor and restored in its destructor. They bracket the `operator()` call, including any inline start of the task. A task that a queuing executor runs later reinstalls TLS from its environment.
====

== Frame Allocator Mixin

Most users never need to allocate coroutine frames manually -- cpp:task[task<T>] and the built-in xref:glossary.adoc#awaitable[awaitable] types already participate in TLS frame allocation. When you write your own coroutine promise type and want it to use the same fast path, inherit from cpp:frame_alloc_mixin[]:

[source,cpp]
----
include::example$snippets/4h_allocators.cpp[tag=frame_alloc_mixin]
----

cpp:frame_alloc_mixin[] (in `<boost/capy/ex/frame_alloc_mixin.hpp>`) supplies `operator new` and `operator delete` that:

* Read the thread-local frame allocator set by cpp:run_async[] or cpp:run[] (falling back to `std::pmr::get_default_resource()` when none is set).
* Bypass virtual dispatch when that allocator is the default recycling memory resource.
* Store the resolved allocator pointer at the tail of each frame, so deallocation uses the correct resource even if the thread-local allocator has since changed.

This is the same strategy used internally by cpp:context_awaitable_promise_base[]. Use the mixin directly when your promise type does not need the full environment and xref:glossary.adoc#continuation[continuation] support that `context_awaitable_promise_base` provides. The allocation fast path uses thread-local storage and needs no synchronization; the global pool fallback is mutex-protected.
