== The Problem

* A user clicks "Cancel" on a download dialog
* A timeout expires while waiting for a network response
* A connection drops unexpectedly
* An application is shutting down

=== The Naive Approach: Boolean Flags

The obvious solution seems to be a boolean flag:

----

This approach has problems:

* *No standardization* — Every component invents its own cancellation flag
* *Race conditions* — Checking the flag and acting on it is not atomic
* *No cleanup notification* — The worker just stops; no opportunity for graceful cleanup
* *Polling overhead* — Must check the flag repeatedly

=== The Thread Interruption Problem

Some systems support forceful thread interruption. This is dangerous because it can leave resources in inconsistent states—files half-written, locks held, transactions uncommitted.

=== The Goal: Cooperative Cancellation

The solution is *cooperative cancellation*: ask nicely, let the work clean up. The cancellation requestor signals intent; the worker decides when and how to respond.

== {cpp}20 Stop Tokens—A General-Purpose Signaling Mechanism

{cpp}20 introduces `std::stop_token`, `std::stop_source`, and `std::stop_callback`. While named for "stopping," these implement a general-purpose *Observer pattern*—a thread-safe one-to-many notification system.

=== The Three Components

`std::stop_source`::
The *Subject/Publisher*. Owns the shared state and can trigger notifications. Create one source, then distribute tokens to observers.

`std::stop_token`::
The *Subscriber View*. A read-only, copyable, cheap-to-pass-around handle. Multiple tokens can share the same underlying state.

`std::stop_callback<F>`::
The *Observer Registration*. An RAII object that registers a callback to run when signaled. Destruction automatically unregisters.

=== Type-Erased Polymorphic Observers

Each `stop_callback<F>` stores a different callable type `F`. Despite this, all callbacks for a given source can be invoked uniformly. This is equivalent to having `vector<function<void()>>` but with:

* No heap allocation per callback
* No virtual function overhead
* RAII lifetime management

=== Thread Safety

Registration and invocation are thread-safe. You can register callbacks, request stop, and invoke callbacks from any thread without additional synchronization.

== The One-Shot Nature

[WARNING]
====
*Critical limitation*: `stop_token` is a *one-shot* mechanism.

* Can only transition from "not signaled" to "signaled" once
* No reset mechanism—once `stop_requested()` returns true, it stays true forever
* `request_stop()` returns `true` only on the first successful call
* *You cannot "un-cancel" a stop_source*
====

=== Why This Matters

If you design a system that needs to cancel and restart operations, you cannot reuse the same `stop_source`. Each cycle requires a fresh source and fresh tokens.

=== Design Implication

If you need repeatable signals, `stop_token` is the wrong tool. Consider:

* Condition variables for repeatable wake-ups
* Atomic flags with explicit reset protocol
* Custom event types

=== Beyond Cancellation

The "stop" naming obscures the mechanism's generality. `stop_token` implements *one-shot broadcast notification*, useful for:

* *Starting things* — Signal "ready" to trigger initialization
* *Configuration loaded* — Notify components when config is available
* *Resource availability* — Signal when database connected or cache warmed
* *Any one-shot broadcast scenario*

=== Why Not `coroutine_handle::destroy()`?

`std::coroutine_handle::destroy()` is the {cpp}20 primitive that frees a coroutine frame. It is not a cancellation mechanism. It has the same flaw as forceful thread interruption. The coroutine is torn down with no opportunity to complete pending I/O, release locks, or run RAII destructors in the expected order.

Capy exposes cpp:task::handle[handle]`()` and cpp:quitter::handle[handle]`()` so that Capy's own launchers (cpp:run_async[], cpp:run[]) and custom integrations can dispatch coroutines through executors. Calling `destroy()` on such a handle while the coroutine is being awaited by a parent produces undefined behavior: the parent still holds the frame and will destroy it again. A holder that must give up a suspended coroutine for good, such as an execution context being torn down, passes its continuation to cpp:abandon[] instead, which unwinds the chain from the top on its owner's executor.

The rule:

* To cancel work, request a stop on a `std::stop_source` whose token the work observes. The work unwinds cleanly through `final_suspend` and any RAII guards run in the correct order.
* Do not call `destroy()` on a handle returned by cpp:task::handle[handle]`()` or cpp:quitter::handle[handle]`()` while the coroutine is being awaited.

== OS Integration

When Capy's I/O is provided by Corosio, requesting stop cancels work in progress rather than waiting for the operation to finish on its own. Corosio cancels the pending operation through whatever backend is active for the platform, and it resolves promptly with `std::errc::operation_canceled`.

The mechanism depends on the backend. Completion-based backends (Windows IOCP, and io_uring when enabled on Linux) cancel the operation in the kernel. Readiness-based backends (Linux epoll, kqueue on the BSDs and macOS, and the portable select fallback) remove it from the reactor before its system call runs. Either way the operation is reported as cancelled instead of blocking until the I/O would have completed.

. The caller owns a `std::stop_source`.
  It passes the token of the source to cpp:run_async[], which puts the token in the environment of the task.
. The task starts, as in xref:index.adoc#how-a-task-runs[How a Task Runs].
  Every task that it awaits gets the same stop token.
. The task awaits an I/O awaitable.
. The I/O awaitable registers a `std::stop_callback` on the stop token.
. The task suspends, and the thread goes back to the executor.
. The caller calls `request_stop()` on the source.
  The stop callback runs at once, on the thread of the caller.
. The stop request and the completion of the operation race.
  The I/O awaitable uses one atomic claim to pick the winner.
  If the stop request wins, the I/O awaitable posts the task to the executor.
  It does not resume the task on the thread of the caller.
. The executor resumes the task.
  The result of the operation compares equal to cpp:cond::canceled[cond::canceled].
. The task finishes.
  It can return the error, throw, or handle the cancellation itself.
. cpp:run_async[] calls the completion handler with the result of the task.

If the operation completed first, the stop callback does nothing.
The completion resumes the task with the result of the operation, as in
xref:index.adoc#how-a-task-runs[How a Task Runs].

In both cases the task resumes and returns through its own code.
Abandoning a chain is different: its frames are destroyed without resuming.
xref:4.coroutines/4j.lifetimes.adoc#_who_owns_a_suspended_coroutine[Who Owns a Suspended Coroutine] explains when that happens.

[WARNING]
====
The stop callback runs on the thread that calls `request_stop()`, at the same time as code on the executor.
Do not assume that all code in an I/O awaitable runs on the executor.

* In the stop callback, touch the state of the I/O awaitable only through the atomic claim.
* Only the side that wins the claim posts the task.
  The side that loses does not touch the I/O awaitable again.
  If both sides post the task, the task resumes twice.
* After the operation can be claimed, the winner can resume the task on another thread before `await_suspend` returns.
  The task can then finish and destroy the I/O awaitable and its environment while `await_suspend` still uses them.
  The example in the next section makes the winner wait until `await_suspend` is done.
====

cpp:async_waker[] is a complete I/O awaitable that implements this sequence, including the atomic claim.
It does not make the winner wait for `await_suspend`, so it requires a single-threaded executor or a strand.
The next section shows the stop callback in detail.

[[stoppable-awaitables]]
== Implementing Stoppable Awaitables

The examples above show *polling* for cancellation with `token.stop_requested()`. For awaitables that suspend indefinitely—waiting for I/O, a lock, or an external event—you need a `std::stop_callback` to wake the coroutine when cancellation arrives.

=== The Dangerous Pattern

A `std::stop_callback` fires synchronously on whatever thread calls `request_stop()`.
The callback must not call `resume()` on the coroutine handle, because every resumption goes through the executor.
xref:4.coroutines/4e.context-awaitable.adoc#stop-callbacks-must-post-not-resume[Stop Callbacks Must Post, Not Resume] explains why.

The next obvious solution, posting the coroutine through the executor, is also wrong:

[source,cpp]
----
include::example$snippets/4f_cancellation.cpp[tag=post_without_claim,indent=0]
----

The stop callback posts the coroutine without checking whether the read already completed.
The completion posts it without checking whether a stop request already did.
When the read completes at about the same time as a stop request, both post, and the coroutine resumes twice.
The second resumption runs a coroutine that has already moved on, or whose frame is already destroyed.

This bug is a race.
Tests rarely trigger it, and under load it shows up as a crash or as memory corruption in unrelated code.

=== The Correct Pattern: Claim, Then Post

Posting the coroutine through the executor is necessary, but it is not enough.
The stop callback and the completion of the operation race, so each one must first win the claim:

* `read_op::claim` is the atomic claim. Only the winner writes the result.
* `arrivals_` makes the winner wait for `await_suspend`.
  The winner and the end of `await_suspend` both arrive, and the second to arrive resumes the coroutine.
  If `await_suspend` arrives second, it resumes the coroutine directly, because it already runs on the executor.
  If the winner arrives second, it posts the coroutine through the executor.
