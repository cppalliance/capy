= Starting Coroutines
:page-mode: how-to

Capy tasks are xref:glossary.adoc#lazy[lazy]: they do not execute until something drives them. Two mechanisms exist:

* *Awaiting*: One coroutine awaits another (`co_await task`)
* *Starting*: Non-coroutine code initiates execution (cpp:run_async[])

Non-coroutine code must start the first task in a chain explicitly.
xref:index.adoc#how-a-task-runs[How a Task Runs] shows both mechanisms as a sequence diagram.
xref:4.coroutines/4d.executors.adoc[Executors and Execution Contexts] introduces the executors and thread pools this page uses.

[NOTE]
====
When a task is awaited, the awaiting coroutine provides its execution environment.
The environment holds an xref:glossary.adoc#executor[executor] for dispatching completion and a xref:glossary.adoc#stop-token[stop token] for xref:glossary.adoc#cancellation[cancellation].
It also holds the frame allocator and the owner that teardown uses to unwind the chain.
====

=== Two-Call Syntax

Call cpp:run_async[] with the executor first, then call the result with the task: cpp:run_async[]`(executor)(task)`.

[NOTE]
====
The two calls rely on {cpp}17 evaluation order.
{cpp}17 guarantees that in the expression `f(a)(b)`:

1. `f(a)` is evaluated first, producing a callable
2. `b` is evaluated second
3. The callable is invoked with `b`

The task's xref:glossary.adoc#coroutine-frame[coroutine frame] is allocated during step 2, and cpp:run_async[] sets up thread-local allocator state in step 1. The task inherits that allocator.
====

[WARNING]
====
Construct the task as the direct argument of the two-call expression. Three
patterns split the two calls apart, and the compiler catches only part of the
first one.

*Stored wrapper.* Storing the result of cpp:run_async[]`(executor)` and calling
it later as an lvalue does not compile, because the wrapper's call operator is
rvalue-qualified:

.Does not compile
[source,cpp,role=pseudocode]
----
auto wrapper = capy::run_async(pool.get_executor());  // Don't do this
wrapper(compute());  // Error: operator() requires an rvalue
----

Calling `std::move(wrapper)(compute())` compiles. It allocates from the right
resource only if nothing changes the thread-local frame allocator in between.
Creating or destroying another wrapper changes it, as does any `co_await` or
task start. The compiler cannot catch that misuse.

*Preconstructed task.* Storing the *task* in a local and passing it in
afterwards compiles and runs. Its frame is allocated by the time the wrapper
exists, so it never sees the wrapper's allocator. A moved-from local, or a task
returned by an earlier statement, behaves the same way.

*Wrapper function.* A helper that accepts a task and performs the two-call
pattern internally has the same effect. Its caller constructs the task as an
argument to the helper, which is before the helper's body runs.

The preconstructed-task and wrapper-function patterns produce no diagnostic at all: the task runs, on a
coroutine frame that came from the wrong allocator.
cpp:run_async_wrapper[] documents each pattern, and
xref:4.coroutines/4h.allocators.adoc#two-call-rationale[Frame Allocators] carries the
{cpp}17-evaluation-order rationale.

Always use the two-call pattern in a single expression.
====

=== Completion Handler Overloads

cpp:run_async[] accepts optional xref:glossary.adoc#completion-handler[completion handlers] for results and exceptions:

[source,cpp]
----
include::example$snippets/4c_launching.cpp[tag=handlers,indent=0]
----

When no completion handler for the result is provided, the result is
discarded. An exception that goes unhandled calls `std::terminate`. That
happens when no completion handler for exceptions was supplied, or when a
completion handler let one escape. To react to an error, pass a completion
handler for exceptions. It receives the `std::exception_ptr` and should
handle it in place rather than rethrowing. If the task is abandoned before it
completes, as a context's teardown does, no completion handler is called.
To catch an error, `co_await` the work inside a coroutine
and use `try`/`catch` rather than starting it fire-and-forget.

=== Executor Affinity

By default, a task inherits its caller's executor. This means completions are dispatched through that executor, ensuring thread affinity for thread-sensitive code.

A cpp:run[] overload that takes an executor overrides this inheritance for a specific child task, binding it to that executor. When it completes, the parent task resumes on its original executor.

This pattern is useful for:

* Running CPU-intensive work on a thread pool
* Performing I/O on an I/O-specific context
* Ensuring UI updates happen on the UI thread

== Stop Token Propagation

Both cpp:run_async[] and cpp:run[] propagate stop tokens to the task they start and all tasks it awaits. The task accesses its token via `co_await this_coro::stop_token`.
